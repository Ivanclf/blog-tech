计网协议杂记

URL

URL（Uniform Resource Locator，统一资源定位符）用于定位网络上的资源，Web 浏览器通过 URL 从 Web 服务器请求页面。其一般格式为：

[] 中的内容均可省略。#fragment 由客户端（浏览器）使用，用于定位页面内的锚点，不会随请求发送给服务器。

除了 URL，还有 URI 的概念。URI（Uniform Resource Identifier，统一资源标识符）用于唯一标识一个资源。URL 是 URI 的子集，它不仅标识资源，还给出了访问该资源的具体方式（协议、主机、路径等）；另一个子集是 URN，仅通过名称标识资源，不涉及位置。

MIME简述

MIME（Multipurpose Internet Mail Extensions，多用途互联网邮件扩展）不是一种传输协议，而是一套内容格式标准。它通过在邮件头中添加一系列字段，使 SMTP 协议能够传输非 ASCII 字符（如中文）、富文本（HTML）以及二进制文件（如图片、音频、文档等附件）。它定义的 Content-Type 标准（即“媒体类型”）非常实用，因此也被直接采纳并应用于 WWW 及其他互联网协议中。

媒体类型（也通常称为 MIME 类型）是一种标准，用来表示文档、文件或一组数据的性质和格式。浏览器通常根据 MIME 类型而非文件扩展名来决定如何处理响应内容。

其格式为 type/subtype，即一个主类型加一个子类型。主类型分为独立（discrete）类型和多部分（multipart）类型：前者是单一的文件或数据，后者由多个部分（part）组成，每一部分都可以是独立的数据块或文件。

RESTful API

RESTful API 也叫 REST API。REST 是 Representational State Transfer（表述性状态转移）的缩写。REST API 通过一组请求方法，表明要对给定资源执行的期望操作。

方法名 说明
GET 获取指定资源，只读且幂等
POST 向服务器提交数据，通常用于创建新资源，不幂等
HEAD 与 GET 相同，但只返回响应头，没有响应体
PUT 用请求体整体替换目标资源，幂等；资源不存在时也可用于创建
DELETE 删除指定资源，幂等
OPTIONS 查询目标资源支持的请求方法，跨域预检请求也会用到
TRACE 回显服务器收到的请求，用于诊断
CONNECT 与代理建立隧道，常用于 HTTPS 透传
PATCH 对资源做局部更新，不幂等

状态码

2xx 成功 3xx 重定向 4xx 客户端错误 5xx 服务器错误
200 OK 301 永久移动到新 URL 400 不良请求 500 服务器错误
201 已创建资源 302 找到（临时重定向） 401 未认证（常译“未授权”），缺少凭证或凭证无效 502 网关错误
202 已接受，但尚未处理完成 303 见其他，要求客户端改用 GET 访问另一个 URI 403 禁止访问 504 网关超时
204 无内容，响应中没有响应体 304 未修改，协商缓存命中，仅返回响应头 404 未找到
307 临时重定向，严格保持原请求方法与请求体 405 方法不允许
406 不可接受，无法提供客户端要求的媒体类型
412 前提条件失败，如 If-Match 等请求头校验不通过
415 不支持的媒体类型，请求体的 Content-Type 不被支持

命名规范

  • 网址和接口中不能有动词，只能有名词，API 中的名词也应该用复数
  • 不用大写字母，建议用 - 而不是 _
  • 善用版本化 API

WebSocket

和 HTTP 的区别

WebSocket 是一种全双工通信协议，建立连接后客户端与服务器均可主动发送数据；而 HTTP 采用请求-响应模型，通信只能由客户端发起，服务器无法主动向客户端推送消息。

WebSocket 使用 ws:// 或 wss://（加密版，基于 TLS）作为协议前缀，与 HTTP/HTTPS 不同。

WebSocket 支持扩展（Extension）与子协议（Subprotocol）机制：扩展用于修改协议的传输行为，子协议用于让双方协商上层应用协议。

WebSocket 的帧头较小（2~14 字节，视载荷长度与掩码而定），不像 HTTP 每次都要携带完整首部，因此网络开销更小。

注意，WebSocket 连接需要先通过一次 HTTP Upgrade: websocket 握手建立，握手成功后双方才切换到 WebSocket 协议通信。

与 SSE 的区别

SSE（Server-Sent Events）是基于 HTTP 的服务器单向推送技术，用于服务器向浏览器持续推送消息。它本质上是一个保持打开的 HTTP 响应：服务器不断以 text/event-stream 格式写入事件流。由于复用现有 HTTP 基础设施，实现较为简单，且浏览器端 EventSource 内置了自动重连与 Last-Event-ID 续传能力。目前它是大模型流式响应的常用技术选择。

相比之下，WebSocket 是独立协议，天然支持双向通信，但连接管理、心跳保活与断线重连都需要自行实现，复杂度更高。

网关往往会有统一封装结果类的操作，但注意不要对 WebSocket 或 SSE 的数据套用这种封装：二者都是持续推送模型，一次连接或一次响应会返回多条消息，而统一结果类适用于“一次请求对应一次完整返回”的语义，两者不匹配。
