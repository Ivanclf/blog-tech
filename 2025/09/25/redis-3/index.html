高并发下的 redis 缓存策略 - 3

Redis 的其他应用

除了做缓存，Redis 的几种数据结构本身就能当组件用。

阻塞队列

抢单、秒杀这类场景，瞬时请求远超数据库的写入能力。读写分离解决不了——它只分摊读，写还是全压在主库上。要挡的是写，靠的是队列削峰：请求先入队、立刻返回，后台按数据库扛得住的速率慢慢消费。

阻塞队列就是“空时取会等、满时放会等”的队列：

  • 空时取：BLPOP key timeout 挂着等，有元素立刻返回，超时则返回 nil；
  • 满时放：Redis 的 List 没有容量上限，得业务层自己查 LLEN。

Java 侧对应 BlockingQueue（ArrayBlockingQueue、LinkedBlockingQueue）。

局限也明显：不持久化、没有 ack，消费者崩溃消息就没了，多个实例争抢消费也不好做。它能削峰，但保证不了可靠投递。

消息队列

消息队列 = 阻塞队列 + 持久化 + 消费确认 + 消费组。Redis 自己有三代方案：

方案 版本 做法 问题
List 早期 LPUSH 写、BRPOP 取 弹出即删，消费者崩溃就丢消息；无消费组、无广播
Pub/Sub 2.0 PUBLISH / SUBSCRIBE 不持久化，没有订阅者时消息直接丢
Stream 5.0 XADD 追加，XREADGROUP 按组读，XACK 确认 功能齐全，但内存占用高，集群下同一 key 只能落一个 slot，大流量不如专业 MQ

生产上主流仍是 RocketMQ / Kafka / RabbitMQ：天然持久化、有消费组与重试、支持堆积。Redis 的 Stream 适合轻量场景，不适合当核心消息总线。

Feed 流

Feed 流是“持续下拉就能刷到新内容”的信息流，分两类：按时间排序（关注、朋友圈）和按算法推荐（抖音、小红书）。这里只谈前者。

模式 做法 优点 缺点
拉（读扩散） 发布者只写自己的发件箱；用户打开时，把所有关注者的发件箱拉过来归并排序 发布零额外开销，省内存 关注多时要遍历很多发件箱，读慢
推（写扩散） 发布时直接写进每个粉丝的收件箱 读只需打开自己的收件箱，快 一条内容写 N 份，大 V 有千万粉就要写千万次
推拉结合 普通用户推、大 V 拉；或活跃粉丝推、僵尸粉拉 兼顾存储与速度 实现复杂

本质就是写时多干活还是读时多干活。粉丝量小用推，大 V 云集用推拉结合。

存储上收件箱用 ZSet，score 存时间戳，ZREVRANGE 直接取最新 N 条。

一年 365 位，一个用户只占 46 字节；换 Set 存 id，千万用户就是几百 MB。

统计：PV 与 UV

指标 含义 做法
PV（Page View） 每访问一次算一次，不去重 INCR page:1:pv
UV（Unique Visitor） 同一用户一天只算一次 HyperLogLog

UV 难在去重还得省内存。Set 精确但占地（千万级几百 MB）；HyperLogLog 固定 12 KB 就能估出任意大集合的基数，标准误差 0.81%。

它只出数字，取不出是谁；要名单或要精确值，还得用 Set 或落库。

GEO

按经纬度存取、按距离查询。底层还是 ZSet：用 GeoHash 把经纬度压成 52 位整数当 score，位置相近则 score 相近，范围查询就退化成 ZSet 的区间查询。

score 已被编码占用，所以不能把 GEO key 当普通 ZSet 用。精度是米级误差，不适合精确定位。

搜索引擎

Redis 自己不做搜索，靠模块：RediSearch 提供二级索引与全文检索，RedisJSON 存 JSON 并按路径查。Redis 8 已把这两个模块并入发行版。

RediSearch Elasticsearch
定位 给已在 Redis 里的数据加查询能力 专门的搜索引擎
数据量 千万级以内 亿级以上，水平扩展
能力 条件、前缀、全文、基础聚合 相关度排序、复杂聚合、分析、可视化
运维 复用 Redis，成本低 独立集群，成本高

小项目、数据本来就在 Redis 里，用 RediSearch 省一套中间件；要做复杂检索、日志分析、大规模聚合，直接上 ES。

分布式

OPPO 后端工程师 - 实习, 二面

四种部署形态，逐级往上加能力：

模式 解决什么 局限
单点 无 挂了就没了
主从 读扩展 + 一份热备 主节点挂了得人工切换
哨兵 自动故障转移 数据还是全在一台上，装不下
集群 分片扩展容量 不支持多 key 的跨槽操作

主从

一个主节点负责写，多个从节点负责读，从节点同时充当热备。Redis 用 replicaof（旧命令 slaveof）建立复制关系。

主节点的写命令会先存在一个固定大小的环形缓冲区里，从节点断线重连后，只要偏移量还落在缓冲区范围内，就能只补发这一段；超出范围就只能全量重传。缓冲区越大、存活越久，越不容易触发全量同步

常见拓扑：一主一从、一主多从、树状主从（从节点再挂从节点，分担主节点的复制压力）。

复制流程分三步：

  1. 建立连接：从节点连上主节点，发送 PSYNC（Redis 2.8 前是 SYNC），带上自己记录的偏移量；主节点为它创建客户端上下文，并开始把写命令写进复制积压缓冲区。

  2. 数据同步：分两种情况。

    • 全量同步：从节点首次连接，或偏移量已被挤出缓冲区。主节点 fork 子进程生成 RDB，期间新写的命令先缓存；RDB 传完后从节点清空本地数据并加载，再接收这期间积攒的命令。
    • 增量同步：偏移量仍在缓冲区内。主节点只把该偏移量之后的那一段命令发过去，断线恢复很快。

  3. 命令传播：之后主节点每处理一条写命令，就异步转发给所有从节点，持续同步。

两个代价：

  • 异步复制会丢数据。主节点写完就回响应，不等从节点确认。主节点在“已回复客户端、命令还没传到从节点”这个窗口里挂掉，这部分就丢了。要更安全可以用 WAIT 命令阻塞等待从节点确认，但它只保证“已到达从节点内存”，不保证“已写入磁盘”。
  • 全量同步开销大。要 fork（内存翻倍风险）、生成 RDB、走网络传输，数据大时能把主节点拖慢，甚至拖出更长的同步窗口。

脑裂

网络分区下的数据丢失。主节点和哨兵、从节点之间的网络断了，但它和客户端的连接还正常，于是：客户端继续往这个“假主节点”写，哨兵那边检测不到它、已经选出了新主节点——两个主节点同时对外服务。

网络恢复后，原主节点降级为从节点并触发全量同步，分区期间写进它的数据全被覆盖掉。

这样分区期间主节点早就拒绝写入了，没有新数据可丢，恢复后的全量同步也就不会覆盖任何东西。

哨兵

主从模式的痛点在于：主节点挂了得人工把某个从节点提升上来。哨兵（Sentinel）就是把这个动作自动化——它是一组独立进程，职责只有两件：监控、自动切换。它不存数据，也不代理请求。

最后一个参数要留意：并行为 1 时，从节点是逐个同步新主节点的，切换慢但不会把新主节点压垮；调大能更快恢复，代价是切换瞬间的复制压力更大。

工作原理

哨兵每 1 秒向所有节点发 PING，超时未回复就标记为主观下线（只是“我这个哨兵觉得它挂了”）。然后向其他哨兵确认，赞成票达到 quorum（上面的 2）才升级为客观下线，此时才真正开始故障转移。

故障转移由选出的哨兵领导者执行（见下节），流程是：

  1. 按规则挑出一个从节点（见下节）；
  2. 向它发 REPLICAOF NO ONE，让它停止复制、升为主节点；
  3. 向其余从节点发 REPLICAOF <新主节点>，让它们改投新主；
  4. 通过发布/订阅通知客户端主节点已变。

四步可归纳为：定时监控 → 主观下线 → 领导者选举 → 故障转移。

部署要求：至少 3 个哨兵，且不在同一台机器上，quorum 一般取哨兵数的一半加一。只有 2 个哨兵时，任何一方网络抖动都可能导致票数不够，反而容易出现误判。

领导者选举

这一步和 Raft 类似，但不是 Raft——只有投票，没有日志复制。

  • 任何确认主节点客观下线的哨兵都可以发起：把自己的纪元（epoch，全局递增的选举轮次）加一，投自己一票，再广播拉票。
  • 每个哨兵在同一纪元内只投一次，投给第一个向它拉票的人。
  • 票数超过哨兵总数的一半即当选。
  • 没选出就等待一个随机时长（防止同时再起冲突），纪元加一后重来。

挑选新主节点

先剔除不合格的：已下线、连接不稳定、replica-priority 为 0（明确不参选）。剩下的按优先级排序：

  1. replica-priority 越小越优先（Redis 5.0 前叫 slave-priority）；这个值配一样时进入下一条；
  2. 复制偏移量越大越优先——数据最新，丢得最少；
  3. 还相同就比较 runid 字典序，小的优先。确定即可，只为消除随机性。

确定人选后，发 REPLICAOF NO ONE 升主，再用 INFO replication 确认其 role:master，最后把其余从节点指向它。

集群

哨兵解决了“挂了自动切”，但数据仍然全在一台机器上——单机内存装不下。集群（Cluster）的做法是把数据分片到多个主节点，加机器就能同时加容量和吞吐。

OPPO 后端工程师 - 实习, 一面

集群在 CAP 里选的是 AP：主节点写完就回响应，异步复制给从节点，failover 也是异步的。所以它只保证最终一致，不是 CP。WAIT 命令能让主节点阻塞到指定数量的从节点确认，但它只收窄了丢失窗口，不等于强一致。

redis cluster

Redis 官方的分片方案。每个节点打开 cluster-enabled yes，再用 cluster meet <ip> <port> 逐个握手加入，就组成了一个集群。

三个核心特性：

特性 说明
分片 全集群共 16384 个哈希槽，每个主节点分一段。键先算 CRC16(key) % 16384 得到槽号，再看槽归谁
高可用 仍是主从结构，每个主节点配一个从节点；主节点挂了，从节点被投票提升
无中心 没有代理节点，每个节点都持有全量集群元数据（谁在线、谁负责哪些槽、谁是主/从），用 Gossip 协议互相同步

通信

节点 A 执行 cluster meet B 后，A 会为 B 建一个 clusterNode 并发出 MEET；B 回 PONG；A 再发 PING 确认——三次交互完成握手（形似 TCP 三次握手）。

握手后，A 用 Gossip 把 B 的信息带给集群里的其他节点，其他节点再各自与 B 握手，很快全网都认识 B。

日常运行靠两种消息：每秒随机挑几个节点发 PING（维持心跳与信息交换），以及节点间定期全量交换元数据。某节点长时间不回 PING 就标记为主观下线；超过半数主节点都认为它下线，才升级为客观下线。

动态伸缩

伸缩的本质就是搬槽，全程可以在线做——靠的是 MOVED / ASK 重定向。

MOVED：槽的归属已经永久变更。客户端请求了不归本节点的键，节点回 MOVED <槽> <新节点IP:端口>，客户端把槽位表更新后直连新节点。发生在迁移完成之后。

ASK：槽正在迁移。请求的键如果已搬到目标节点，源节点回 ASK <槽> <目标节点IP:端口>，客户端这次临时去目标节点取，但不更新本地的槽位表。因为迁移还没结束，这个槽整体仍归源节点。

MOVED 是“这槽以后归它了，记住”；ASK 是“这个键现在是它管，这次去找它，别记”。

批量操作

一条命令的耗时由四段组成：发指令 → 服务端排队 → 执行 → 回结果。其中第 2、3 段是 Redis 本身在干活，快；第 1、4 段是网络往返（RTT），才是耗时大头。批量操作做的就是把这 N 次往返压成 1 次。

原生批量命令

MGET / MSET / HMGET / HMSET 这类命令本身接受多个 key，天然省往返。注意 SADD 不是“批量命令”，它只是恰好可以一次传多个 member。

局限在集群下暴露：分片按 key 算槽，MGET k1 k2 里两个 key 若不在同一个槽，就无法一条命令完成——客户端得自己按槽拆分、分头发送。所以跨槽批量只能靠哈希标签 {} 把 key 绑到同槽。

至于“原子性”，MGET/MSET 这类多 key 命令是原子的（Redis 单线程，执行期间不会插别的命令）；但客户端拆成多次发送后就不再是一个整体了。

Pipeline

不想凑、也凑不成批量命令时，用 pipeline：客户端把 N 条命令一次性写进 socket，不等回复就接着发下一条；服务端按序执行，把结果一次性批量返回。往返从 N 次变成 1 次。

它不是越大越好：一批太大会阻塞这条连接、占用服务端输出缓冲（client-output-buffer-limit），还可能一次积压几十 MB 结果。一般每批 1000~5000 条。

pipeline 与事务的区别

常见误解是“事务是原子的，pipeline 不是”，这个说法不准确：

Pipeline MULTI / EXEC 事务
网络往返 1 次 1 次（命令也会一起发出，不是每条一次）
中间能插别的客户端命令吗 能，不保证连续 不能，EXEC 时整批连跑
出错处理 一条失败，其余照常执行 同样不回滚，一条失败其余照常
普通用途 减少 RTT，追求吞吐 配合 WATCH 做乐观锁，或要求命令连续执行

所以两者的差别不在“原子”，而在是否保证这批命令之间不被其他客户端的命令插入；以及事务能配 WATCH 做 check-and-set。真正需要“读-改-写”不被打断的，应该用 Lua 脚本，它才具备完整的原子执行。
