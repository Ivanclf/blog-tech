高并发下的 redis 缓存策略 - 1

Spring MVC 一般跑在 Tomcat 这类 Servlet 容器上：一个请求占用一个容器线程，从进到出。请求一多，线程都卡在等数据库上，响应自然慢。缓存要做的就是把重复的读请求挡在数据库之前，Redis 就是这一层。

“Redis 单线程工作，单线程指的是命令执行——不用加锁，也就没有线程安全问题。至于同时服务上万个连接，靠的是 IO 多路复用（epoll），一个线程监听多个连接，这不是多线程。

后续版本只是把一部分工作挪出了主线程：

版本 变化 目的
4.0 增加后台线程做异步删除（UNLINK、FLUSHALL ASYNC 等） 删大 key、清库不再阻塞主线程
6.0 网络 IO 与协议解析交给 IO 线程池，命令执行仍是单线程 分摊网络开销，提高吞吐

单机 QPS 通常在 10 万量级。

点击这里学 redis 基础命令。Java 中一般用客户端库操作 Redis，如 Jedis、Lettuce、Redisson。

为什么需要缓存？

前后端分离项目的链路：

graph LR
frontend[frontend]-->|step 1|backend[backend]-->|step 2|database[database]

多实例部署后，step 1 要加 nginx 做反向代理和负载均衡，但请求最终仍落到同一批数据库上。登录校验、热点数据查询这类大量重复的读会把 MySQL 压垮，所以得在 step 2 插一层内存缓存，把重复读挡在数据库前面。Redis 就是这层缓存。

典型例子：登录状态存在哪？

方案 做法 特点
JWT 登录成功后，后端把用户信息、过期时间等写成 JSON，Base64 编码后拼成 token，再对内容签名后返回客户端；之后每次请求带上它，服务端验签即可 服务端无状态、不用存；但签发后无法主动作废，只能等它过期
Redis 存 token 登录成功后，后端生成随机 token 返回客户端，同时存一份 token → 用户信息 到 Redis；之后每次请求拿 token 去 Redis 查 能随时删 token 让用户下线，也能顺手续期

需要“强制下线”或“活跃即续期”时，后者更合适。

redis 数据类型指北

类型 底层实现 说明
String SDS 最大 512 MB，常用来存序列化后的对象
Hash 元素少用 listpack，超阈值转哈希表 哈希表是数组 + 拉链（没有红黑树）；适合只改某几个字段，或想省内存
List quicklist 多个 listpack（7.0 前是 ziplist）用指针串成双向链表，兼顾内存与两端进出
Set 全整数且量少用 intset，否则哈希表 SRANDMEMBER 随机取元素；SINTER/SUNION/SDIFF 求交/并/差，带 STORE 后缀的会把结果存成新 key
ZSet 跳表 + 字典 跳表管排序和范围查询，字典管 $O(1)$ 由 member 查 score

SDS

Redis 没有直接用 C 的 char *，而是自己实现了 SDS（Simple Dynamic String，简单动态字符串）。换来三个好处：

  • $O(1)$ 求长度：len 字段直接记着，不用像 strlen 那样扫到 \0。
  • 二进制安全：判断结尾靠 len 而不是 \0，内容里可以有 \0，所以能存图片、序列化对象。
  • 预分配 + 惰性释放：free 记录空闲空间，追加时少扩容；缩短时不立刻归还，避免频繁 realloc。

大致结构如下（Redis 3.2 起按长度分为 sdshdr5/8/16/32/64 五种，区别只是 len、free 用 uint8_t、uint16_t、uint32_t 还是 uint64_t）：

跳表

腾讯混元 - 实习, 一面.

超过任一阈值后，ZSet 就变成跳表 + 字典：字典存 member → score，按成员查分数是 $O(1)$；跳表让节点按 score 有序，撑起范围查询。

跳表就是在有序链表上叠多层索引，像坐电梯：先在高层大步跨，跨过头了就降一层细找。

以查 6 为例：

  1. 从最高层出发，在 2 级索引上走到 4；下一个是 8，比 6 大，停。
  2. 降一层，到 4 的 1 级索引，下一个就是 6，命中。

层级是随机的：每个节点先定 1 层，之后每轮以概率 $p$ 再加一层（Redis 取 $p=0.25$，最高 32 层）。理想情况下每层节点数是下一层的 1/4，步数因此是 $O(\log n)$。用随机代替「必须平衡」，就不用旋转、整树调整：插入是「找前驱 → 掷骰子定层 → 接指针」，删除是「找前驱 → 摘指针 → 必要时降最大层数」。

为什么不用红黑树 / B+ 树：

  • 范围查询：跳表底层就是有序链表，ZRANGE 从定位点顺着走；红黑树得中序遍历，还要维护遍历栈。
  • 实现难度：平衡树靠旋转维持严格平衡，跳表靠概率，代码短、易改。
  • 内存：B+ 树节点要预分配、容易留空洞，跳表每个节点只多几个指针。

字典与渐进式 rehash

Hash、Set 的哈希表、以及整个 Redis 的键空间，底层都是字典：dict → 两个哈希表 ht[0]、ht[1] → 数组 + 拉链。

rehash 的触发条件：负载因子 ≥ 1 扩容（若正在做 RDB/AOF 子进程则放宽到 ≥ 5，避免写时复制放大内存），< 0.1 缩容。

做法是先给空闲的 ht[1] 分配空间（扩容两倍、缩容一半），rehashidx 置 0；之后每次读写字典都顺手把 rehashidx 这一槽位的节点搬到 ht[1]，搬完 rehashidx++。期间查找要查两张表，新增只写 ht[1]；全搬完后交换两张表，rehashidx 复位为 -1。这样把一次大搬迁摊到多次操作上，不会卡住主线程。

过期 key 的删除

四种思路，Redis 只用了后两种：

策略 做法 代价
定时删除 每个 key 挂定时器，到点立刻删 CPU 压力最大，Redis 不用
延迟队列 按到期时间入队，由队列触发删除 要额外维护队列，Redis 不用
定期删除 每秒若干次随机抽查一批，删掉过期的 CPU 可控，内存可能滞留
惰性删除 访问时顺手判断，过期就删并返回 nil 省 CPU，但没人访问的 key 会一直占内存

实际是定期 + 惰性：定期负责兜底清理，惰性兜住漏网的。

定期删除每轮的约束（默认 hz = 10，即每秒 10 轮）：

  • 每轮随机抽 20 个带过期时间的 key；
  • 过期比例超过阈值就接着抽下一批，低于阈值就结束这一轮；
  • 整轮耗时不超过周期的 25%（hz=10 时约 25ms），超了立刻中断，避免拖慢主线程。

dynamic-hz yes（默认开）会在连接数变多时自动调高 hz，过期检查和事件处理也会跟着变频繁。

内存淘汰策略

过期删除管“到期”，淘汰管“放不下”。maxmemory 是内存上限，只管数据本身，不含写时复制的副本、主从缓冲区、内存碎片，所以一般按物理内存的 60%~75% 设。

打满后不再报错或宕机，而是按 maxmemory-policy 删 key：

策略 候选范围 淘汰谁
noeviction — 不淘汰，写命令直接报 OOM（默认值）
allkeys-lru 所有 key 最久没被访问的
allkeys-lfu 所有 key 访问频率最低的
allkeys-random 所有 key 随机
volatile-lru / -lfu / -ttl / -random 设了 TTL 的 key 同上；-ttl 是剩余时间最短的

两个坑：

  • volatile-* 只动设了 TTL 的 key，若这些 key 都无可淘汰，行为退化成 noeviction，照样 OOM。
  • LRU / LFU 都是近似的：随机采样 maxmemory-samples（默认 5）个 key 挑一个淘汰，不维护全局链表。采样越多越准，CPU 开销也越大。

纯缓存用 allkeys-lru；热点长期集中、怕热门被误删用 allkeys-lfu；持久数据和缓存混在同一实例，用 volatile-lru 让缓存先走。

缓存更新

同一份数据存了两份，就有一致性问题：数据库改了，缓存什么时候跟着改？这里有两个决策——改缓存还是删缓存，先动库还是先动缓存。

改缓存还是删缓存

做法 好处 问题
改缓存 命中率高，改完就是新的 并发写会互相覆盖；算出来可能没人读，白费；缓存常是聚合结果，改它等于重算一遍
删缓存 写方只发一个 DEL，不会写出矛盾的值 删除后的第一波读请求会落到库上

一般选删。删掉后由读请求懒加载回填，缓存里永远是某一次读库的结果，不会出现两个写线程各写一半的“拼装数据”。

这就是 Cache Aside（旁路缓存）：业务代码自己管缓存，读时先查缓存、miss 再查库并回填，写时改库 + 删缓存。另外两种是 Read/Write Through（把缓存当主存，由中间件代理读写数据库）和 Write Behind（只写缓存、异步刷库，性能最好但一致性最弱，宕机可能丢数据）。一般项目用 Cache Aside 就够。

先动库还是先动缓存

先删缓存，再改库：从删掉到改完库之间有一段空窗，期间任何读请求都 miss、读库、把旧值写回缓存。改库越慢（大事务、批量更新），空窗越长，脏数据越容易留。这个顺序直接排除。

先改库，再删缓存：脏数据只可能出现在一种交错里——读请求在改库之前读到旧值，却到删缓存之后才回填。这要求一次读操作恰好横跨整个写操作，概率极低。所以一般先改库再删缓存，这也是 Cache Aside 的默认写法。

代价是短暂不一致：删缓存到下一次回填之间，读请求可能仍拿到旧值。大多数业务能接受；若要“读到自己刚写的”，可由写方在本地打标记，随后短时间直读数据库。

追求更强一致性

  • 延迟双删：改库前删一次，改库后再延迟几百毫秒删一次，把晚到的回填脏值清掉。延迟靠估算、不严谨，胜在简单。
  • 订阅 binlog：用 Canal 订阅 MySQL binlog，数据真正落盘后再删缓存。删除动作与业务代码解耦，失败可重试，是生产上最常见的做法。
  • 本地消息表 + MQ：改库事务里顺带插一条消息记录，提交后发 MQ，消费者负责删缓存；删失败靠 MQ 重试最终成功。

前两条解决“删早了”，最后一条解决“删除请求本身丢了”。

改库和删缓存是两个动作，没法真正做到原子，只能靠事务或补偿：

  • 单体应用：库操作放进本地事务，删缓存放到提交之后——事务回滚了就不该删。
  • 分布式：本地事务管不到跨服务，用 TCC 一类补偿事务。

缓存穿透

查的数据根本不存在，缓存永远 miss，每次都穿到库里。正常业务里少见，但一旦有人拿不存在的 id 扫，流量会全部落到数据库上。

方案 做法 代价
缓存空值 查库发现不存在，就往 Redis 写一个空标记，TTL 设短一点 实现最简单；被扫时会造出大量垃圾 key，且与库存在短时间不一致
布隆过滤器 写库时同步写入过滤器，请求先过一遍过滤器，不在里面直接返回 内存开销小；有误判，且不支持删除

两者通常叠加：过滤器挡住绝大多数非法 key，漏过的再用空值兜底。

布隆过滤器怎么工作：一个 bit 数组加 $k$ 个哈希函数。写入元素时，把每个哈希算出的位置置 1。查询时只要有一位是 0，就一定不存在；全是 1，只是可能存在。所以它只会误判“存在”，不会漏掉真实存在的 key。过滤器的误判率随元素数量上升，所以容量要按预期数据量预留。标准布隆过滤器不能删元素（把位清零会误伤其他元素共享的位），需要删除就用计数布隆过滤器，把每个位换成计数器，代价是内存涨数倍。

接口层还要配合参数校验、限流、封禁可疑 IP。过滤器只能挡“格式合法的假 id”，挡不住真正的恶意流量。

缓存雪崩

大量 key 在同一时刻失效，或者 Redis 整体不可用，流量瞬间全压到数据库。原因不同，应对也不同：

原因 应对
大量 key 过期时间相同 给 TTL 加随机偏移
刚上线/重启，缓存是空的 预热：用 xxl-job 定时任务或消费 Kafka，把热点数据提前灌进去
Redis 宕机 主从 + 哨兵 / Cluster；再加一层本地缓存 Caffeine 兜住热点（一致性靠 pub/sub 广播或短 TTL 收敛）
流量本身超出承载能力 限流、降级、熔断，把请求挡在入口，别把库拖死

缓存击穿

单个热点 key 失效的瞬间，请求同时回源，把库打穿。它和热 key 是同一件事的两面：热 key 一旦过期就是击穿，即使不过期，也能把单个节点压垮。

热 key

访问高度集中的 key 就是热 key，典型如大促爆款、首页榜单。它的危害在于压力集中在一个分片——集群加再多节点也没用，同一个 key 只落在一个节点上。

手段 说明
redis-cli --hotkeys 需要 maxmemory-policy 是 LFU 系列（allkeys-lfu / volatile-lfu）才生效
拆分副本 把 key 拆成 N 份（如 item:1001:{0..N-1}），读时随机挑一份，写时广播；适合读多写少
本地缓存 热点数据沉到 JVM（Caffeine），连网络都省了；代价是多实例间要靠 pub/sub 或短 TTL 收敛
读写分离 加从节点分摊读，但数据还是同一份，只能缓解

大 key 是另一类问题：不是 QPS 高，而是单次操作耗时长，可能阻塞主线程拖慢整个节点。用 redis-cli --bigkeys 找出来，拆成多个小 key；JSON 可以先 Gzip 压缩。

击穿的两套解法

互斥锁 逻辑过期
做法 重建前先抢锁（SET NX 或本地锁），抢到的查库写缓存，其余等待或直接返回兜底值 value 里存过期时间戳，物理上不设 TTL；读到逻辑过期后，由一个线程异步重建，其他线程直接返回旧值
优点 一致性强，实现简单 无等待，吞吐高
缺点 线程阻塞；锁要设超时防死锁 重建窗口内返回旧数据，一致性弱
适用 一致性优先：库存、余额 可用性优先：商品详情、榜单、文章

互斥锁不让请求穿透，逻辑过期不让请求等待。选哪个，看这份数据能否容忍几十毫秒的旧值。
