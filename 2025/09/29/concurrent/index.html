并发基础 - 1

概念辨析

并行与并发

并行与并发的区别在于：并行是同一时刻真正同时执行多个任务，需要多个物理执行单元；并发是在一段时间内交替处理多个任务、看起来像是同时运行，只是逻辑上的“同时”。

在单核 CPU 上的多线程程序（靠时间片轮转切换线程），以及 JS 在浏览器主线程中的异步操作，都是并发但不并行的场景；多核 CPU 上的 Web 服务器、分布式系统中的微服务，则是既并发又并行的场景。

异步与并发

异步和并发的区别在于：异步在意“等待”，让调用方在结果就绪前不必原地等待；并发在乎“同时发生”，指多个任务在重叠的时间段内开始、运行和完成，但不一定在同一瞬间完成。

异步和同步的区别在于：同步调用在拿到结果前不返回，调用方必须原地等待；异步调用则立即返回，结果稍后通过回调、事件或通知等方式交回调用方。

同步、异步、阻塞、非阻塞

美团后台开发 - 暑期实习, 一面.

这里实际上是两个维度：同步和异步、阻塞和非阻塞。

维度 含义 关键问题
同步/异步 调用方如何得知结果 同步：调用方主动等待结果
异步：由被调用方在完成后通知
阻塞/非阻塞 等待结果的过程中，当前线程能否做其他事 阻塞：线程被挂起等待
非阻塞：调用立即返回，线程继续执行

两者互不绑定，可以派生出四种组合：

  1. 同步阻塞
    最传统的方式。调用方发起请求后一直等待，线程挂起，直到结果返回。例如普通的 InputStream.read()、JDBC 查询。
  2. 同步非阻塞
    调用方发起请求，若结果未就绪则立即返回，线程不挂起，由调用方稍后主动再问一次。
    例如 NIO 中把 Channel 设为非阻塞后轮询 read()；再如 Spring Task 每隔一段时间轮询数据库，看有没有待处理的数据。
  3. 异步阻塞
    较为少见。调用方发起异步操作后，仍立刻去等那个结果，线程挂起直到结果返回。
    例如 CompletableFuture.get()：任务本身是异步执行的，但调用方选择阻塞等待。
  4. 异步非阻塞
    最理想的模型。调用方发起请求后立即返回，不等待结果；结果就绪时，系统通过回调、事件、信号等方式通知调用方，整个过程中调用方线程从未挂起。
    例如大模型推理、ASR 等耗时较长的处理，SaaS 服务通常提供回调地址，处理完成后主动回调。

同步与互斥

这两个词常被混用，但关注点不同：

关注点 要解决的问题 典型手段
同步 线程之间的协作 让线程按约定顺序推进（“等我做完你再来”） wait / notify、CountDownLatch、CyclicBarrier、Semaphore、join()
互斥 对共享资源的保护 同一时刻只允许一个线程进入临界区 synchronized、ReentrantLock、原子类

一句话概括：互斥回答“谁能进”，同步回答“什么时候能进”。

两者不是并列关系：互斥是同步的一种特例；反过来，同步不一定要互斥——CountDownLatch 只负责“等齐了再放行”，全程不阻止任何线程访问共享资源。

实际场景里两者往往同时出现。以生产者-消费者为例：队列空时消费者要等、队列满时生产者要等，这是同步；而 put() / take() 内部对底层数组的读写必须串行，这是互斥。BlockingQueue 把两者封装在了一起。

概述

JDK 1.2 之前，Java 线程就是用户线程。JDK 1.2 后，Java 采用一对一内核线程映射模型，每创建一个 Thread 对象并调用 start() 方法时，JVM 会通过操作系统原生 API 向内核申请创建对应的原生操作系统线程，Java 线程的生命周期、调度完全交由操作系统内核调度器管理。

Java 的线程和普通线程一样，也需要存储一些私有数据：程序计数器用于线程切换后能恢复到正确的执行位置，虚拟机栈用于存储局部变量表、操作数栈等信息，本地方法栈用于存储 native 方法的相关信息。

创建

创建线程最基础的方式有三种（实际开发中更推荐把任务提交给线程池，见后文）。

第一种是继承Thread并重写其run()方法，然后调用start()方法启动线程。

该方法的缺点是：类一旦继承了Thread，就不能再继承其他类了。

第二种是实现Runnable接口的run()方法，并将实现类的对象作为参数传给Thread的构造方法，最后调用start()方法启动线程。

第三种是实现Callable接口的call()方法，用它创建FutureTask对象，再把该FutureTask对象作为参数传给Thread的构造方法，最后调用start()方法启动线程。

该方法能获取线程的执行结果：FutureTask.get() 会阻塞，直到 call() 返回或抛出异常。

每创建一个线程，JVM 都要为它分配一块独立的虚拟机栈，64 位 HotSpot 上默认大小为 1 MB（不同平台略有差异，可用 -Xss 调整）。

调用start()之后，JVM 会启动一个新的线程，由这个新线程去执行run()方法；而直接调用run()，不过是在当前线程里执行一个普通方法，不会产生任何新线程。start() 之后线程进入就绪状态（在 Java 层面统一体现为 Thread.State.RUNNABLE），等待操作系统调度；一旦被调度到，就会执行其run()方法中的代码。同一个 Thread 对象只能调用一次 start()，重复调用会抛出 IllegalStateException。

Runnable 和 Callable 的区别如下

特性 Runnable Callable
包路径 java.lang.Runnable java.util.concurrent.Callable
方法签名 void run() V call() throws Exception
返回值 无 有
受检异常 不能抛出 可以抛出
适用场景 无需返回结果的任务 需要返回结果或可能抛异常的任务

Runnable 自 Java 1.0 起就存在，而 Callable 在 Java 5 才引入，就是为了补上 Runnable 不支持“返回结果 / 抛出受检异常”的短板。工具类 Executors 可以把 Runnable 转换成 Callable（Executors.callable(Runnable task) 或 Executors.callable(Runnable task, Object result)）。

调度

调度的核心是回答三个问题：线程有哪些操作可以做、每个操作把它变成什么状态、以及这个操作会不会释放它已经持有的锁。

总结

  1. 调度权在内核，Java 只能“提建议”。JDK 1.2 之后 Java 线程与内核线程一对一映射，真正决定谁上 CPU 的是操作系统调度器。setPriority()（取值 1~10，默认 5）和 yield() 都只是提示，既不保证执行顺序，也不保证让出的时机，不能当作同步手段使用。

  2. 不同操作对应不同状态，也对应不同的锁行为：

操作 进入的状态 是否释放持有的锁 何时恢复
start() RUNNABLE（就绪，等待调度） — 被调度器选中
sleep(ms) TIMED_WAITING 否 睡满 / 被中断
wait()、wait(ms) WAITING、TIMED_WAITING 是（释放所在对象的锁） notify / notifyAll / 超时 / 被中断
join()、join(ms) WAITING、TIMED_WAITING 不释放业务对象锁（底层是在目标线程对象上 wait()） 目标线程结束 / 超时 / 被中断
yield() 仍为 RUNNABLE 否 随时可能再次被调度

  1. 等待 / 唤醒定义在 Object 上，不在 Thread 上。它们操作的是某个共享对象的等待集合，所以调用前必须持有该对象的监视器，否则抛 IllegalMonitorStateException。被唤醒的线程不会立刻恢复运行，而是从等待集合转到该对象的锁竞争队列（BLOCKED），重新拿到锁后才继续执行——因此 notify() 之后并不会马上释放锁，要等持有者退出同步块。另外 notify() 只随机唤醒一个等待线程，存在唤醒“错误线程”导致其他线程一直等下去的风险，一般优先用 notifyAll()。

  2. 中断是协作式取消，不是强制终止。interrupt() 只把目标线程的中断标志置为 true：如果此时它正阻塞在 sleep、wait、join 等可中断方法上，这些方法会抛 InterruptedException 并清除中断标志；否则线程照常往下跑，需要自己在合适的检查点上判断并退出。isInterrupted() 只查不清，静态的 Thread.interrupted() 查完即清。捕获 InterruptedException 后不要静默吞掉，要么向上抛，要么调用 Thread.currentThread().interrupt() 把标志恢复给上层。

  3. 守护线程跟着“非守护线程”一起收场。只有当所有非守护线程都结束后，JVM 才会退出并强制结束所有守护线程，所以守护线程的 finally 块不保证执行，不适合承担落盘、提交事务这类收尾工作。守护属性必须在 start() 之前设置，否则抛 IllegalThreadStateException。

通信

线程之间通信无非两类需求：传递数据和协调顺序。JUC 把常见的协作模式抽象成了若干同步器：

方式 核心类 作用 典型场景
阻塞队列 BlockingQueue 一方放入、一方取出，队列空或满时自动阻塞 生产者-消费者
信号量 Semaphore 限制同时访问某类资源的线程数 连接池、限流
互斥 synchronized、ReentrantLock 同一时刻只允许一个线程进入临界区 保护共享变量
交换器 Exchanger 两个线程在会合点互换数据 双缓冲
等待/通知 Object.wait() / notify() 线程等待某个条件，由其他线程唤醒 自定义条件队列
倒计数门闩 CountDownLatch 等待 n 个事件全部发生后放行，一次性 主线程等所有子任务就绪
循环栅栏 CyclicBarrier n 个线程互相等到齐再一起继续，可重复使用 分阶段并行计算
阶段器 Phaser 可复用、参与者可动态增减的栅栏 多阶段任务
管道 PipedInputStream / PipedOutputStream 两个线程间单向传字节流 基本被阻塞队列取代

阻塞队列

最常用的方式，标准的生产者-消费者实现。put() / take() 都是阻塞操作：队列满了 put() 等待，队列空了 take() 等待，天然形成背压，不会像无界队列那样把内存撑爆。

常见实现：ArrayBlockingQueue（数组，必须指定容量）、LinkedBlockingQueue（链表，可指定容量）、SynchronousQueue（不存元素，只做线程间直接交接）、PriorityBlockingQueue（按优先级出队）、DelayQueue（到期才可出队）。线程池的 workQueue 用的就是它们。

信号量

信号量是对 PV 操作的封装。acquire() 获取一个许可，没有剩余许可就阻塞；release() 归还许可。许可数大于 1 时用于限流，等于 1 时退化为互斥锁。

与锁的关键区别在于：锁只能由持有它的线程释放，而信号量任何线程都可以 release()，因此它表达的是“资源数量”而不是“谁持有”。典型用途是数据库连接池、接口限流，new Semaphore(n, true) 可开启公平模式。

互斥

最基础的同步手段，保证临界区的串行执行。synchronized 是 JVM 内置的监视器锁（管程），进出自动加锁解锁；ReentrantLock 是 JUC 提供的显式锁，必须自己在 finally 里 unlock()，但换来了可中断、可超时、公平锁、多个 Condition 等待队列等能力。两者都可重入，区别只在灵活性。

ThreadLocal

字节跳动, 中国交易与广告 - 实习, 一面

ThreadLocal 是一种线程本地变量：同一个 ThreadLocal 对象，在不同线程中 get() 到的是各自独立的值，因此不用加锁就能避开竞争。

常用方法：set(v) 设置、get() 读取、remove() 清除、initialValue() 提供初始值（protected，由子类重写）；Java 8 起更常用的是静态工厂 ThreadLocal.withInitial(Supplier)。get() 查不到值时会调用 initialValue()（默认返回 null）并写入，所以不会因为“没设过”而报错。典型场景是 Session、当前登录用户、Connection、SimpleDateFormat 这类按线程隔离的上下文。

底层结构

数据并不在 ThreadLocal 里，而在 Thread 对象自己的 ThreadLocalMap 字段（threadLocals）中，ThreadLocal 只是操作这张表的句柄。

set(v) 和 get() 都是两步：取当前线程的 ThreadLocalMap（没有就创建），再以 this（ThreadLocal 对象本身）为 key 存取。

ThreadLocalMap 不是 HashMap，而是自己实现的数组 + 线性探测（开放寻址），没有链表；扩容阈值是容量的 2/3。因为一个线程通常只放几个变量，省掉节点对象更划算。

内存泄漏

Entry 继承自 WeakReference<ThreadLocal<?>>，即 key 是弱引用、value 是强引用。引用链是 Thread → ThreadLocalMap → Entry → value，只要线程还活着，value 就一直被强引用着。

于是当业务代码已经不再引用某个 ThreadLocal 时：key 被 GC 回收后变成 null，value 却仍被 Entry 强引用而无法回收；线程不退出，ThreadLocalMap 就不释放，value 长期驻留堆中。

ThreadLocalMap 在 set、get、remove 时会顺带清理 key 为 null 的脏 Entry，但这依赖之后还有操作；若该线程再也不碰这张表，脏 Entry 就永远留着。所以用完必须 remove()，通常放在 finally 里——线程池的线程会被复用，不清理就会串到下一个任务，这是最常见的坑。

key 之所以用弱引用：如果 key 也是强引用，ThreadLocal 对象本身会被 Entry 永久持有，连“判断 key 已失效”的依据都没有；弱引用把不可回收的范围从“ThreadLocal 及其 value”缩小到“仅 value”，同时让清理有了判据。

其他

  • InheritableThreadLocal 让子线程继承父线程的值：Thread 在构造时会把父线程的 inheritableThreadLocals 复制一份给子线程。注意这是创建时的一次性拷贝，此后父子互不影响；线程池里的线程是被复用的、不会重新创建，继承因此失效。
  • 不要用它存大对象或生命周期与线程不匹配的数据。

线程池

基本信息

线程池解决三件事：复用线程（省掉反复创建销毁的开销）、限制并发数（防止把资源打满）、统一管理任务排队与拒绝。核心实现是 ThreadPoolExecutor。

核心参数

参数 含义 要点
corePoolSize 核心线程数 线程数的下限。默认懒创建，提交任务时才建线程，而不是构造线程池时就建满；默认空闲也不回收
maximumPoolSize 线程数上限 只有在任务队列已满之后才会扩容到这里，不是一上来就能用到
workQueue 任务队列 缓存已提交、尚未执行的任务。若用无界的 LinkedBlockingQueue，队列永远不满，maximumPoolSize 就永远不生效
keepAliveTime + unit 空闲存活时间 超过该时间的非核心线程被回收；开启 allowCoreThreadTimeOut 后对核心线程同样生效
threadFactory 线程工厂 自定义线程名、优先级、是否守护、异常处理器，排查问题时很有用
handler 拒绝策略 队列满且线程数已达上限时的兜底动作

前三个参数基本决定了任务的处理策略，其余属于补充控制。

工作流程

  1. 线程数 < corePoolSize：新建核心线程执行任务。
  2. 否则把任务放入 workQueue 排队。
  3. 入队成功：等空闲线程取走执行，本次提交到此结束。
  4. 入队失败（队列已满）且线程数 < maximumPoolSize：新建非核心线程执行。
  5. 线程数已达 maximumPoolSize：交给 handler 处理。
  6. 线程空闲超过 keepAliveTime：非核心线程退出，核心线程默认保留（除非开了 allowCoreThreadTimeOut）。

提交任务

  • execute(Runnable)：无返回值。任务抛出的异常会直接抛给该工作线程的 UncaughtExceptionHandler，并导致这个工作线程终止；线程池随后会新建一个线程补上，池子不会瘫痪，但异常很容易没人发现。
  • submit(...)：返回 Future。异常被封装进 Future，不调用 get() 就永远看不到；调用 get() 时异常会被包成 ExecutionException 抛出。

所以用 submit() 必须消费 Future，否则等于把异常静默丢弃。

Future 表示异步计算的结果，共 5 个方法：

  • boolean cancel(boolean mayInterruptIfRunning)：取消任务，参数表示是否允许中断正在执行的任务
  • boolean isCancelled()：是否已取消
  • boolean isDone()：是否已结束（正常结束、异常结束、取消都算）
  • V get()：阻塞等待结果
  • V get(long timeout, TimeUnit unit)：带超时等待，超时抛 TimeoutException

它的局限在于不支持任务的编排组合，get() 又是阻塞调用，因此 Java 8 引入了 CompletableFuture，提供回调式和函数式风格的组合能力。

需要等多个任务都完成再继续的场景，用 allOf() 很合适：

异常处理用 whenComplete（无论成功失败都回调）、exceptionally（只在异常时兜底）、handle（正常与异常都处理并返回新结果）。CompletableFuture 默认使用 ForkJoinPool.commonPool() 作为线程池。

拒绝策略

策略 行为
AbortPolicy（默认） 抛 RejectedExecutionException
CallerRunsPolicy 由提交任务的线程亲自执行该任务
DiscardPolicy 静默丢弃，不抛异常
DiscardOldestPolicy 丢掉队列头部的任务，再重新提交当前任务

CallerRunsPolicy 能保证任务不丢，代价是把压力反推给提交方：如果提交方是主线程、任务又很耗时，主线程就会被拖住，进而上游堆积甚至 OOM。生产上更常见的做法是把任务先落到 MQ 或本地队列，再实现 RejectedExecutionHandler 自定义降级逻辑。

关闭方式

  • shutdown()：不再接收新任务，队列中已提交的任务和正在执行的任务都会跑完。
  • shutdownNow()：不再接收新任务，尝试中断正在执行的任务，并返回队列中尚未执行的任务列表。注意“中断”能否生效取决于任务是否响应中断，不响应就停不下来。

线程数

顺丰科技 - 秋招, 二面.

线程数取决于任务类型：

  • CPU 密集型：N + 1。线程大部分时间在计算，多开只会增加上下文切换开销；+1 用来兜住偶发的页缺失或短暂阻塞。
  • IO 密集型：N × (1 + 等待时间 / 计算时间)。线程等 IO 时会交出 CPU，所以可以多开，等待占比越高能开的越多。经验值常取 2N。

实际配置还要结合监控：CPU 使用率低而队列持续积压，说明可以加线程；CPU 已接近打满、吞吐却上不去，说明再加只是换来更多上下文切换。

常见的线程池

Executors 提供了四种预设：

工厂方法 线程数 任务队列 特点与风险
newFixedThreadPool(n) 固定 n LinkedBlockingQueue（无界） 并发数可控，适合负载稳定、需要限制并发的场景；队列无界，任务积压会 OOM
newCachedThreadPool() 0 ~ Integer.MAX_VALUE SynchronousQueue（不存储） 有任务就建线程、空闲 60 秒回收，适合大量短任务；线程数无上限，突发流量会打爆资源
newSingleThreadExecutor() 1 LinkedBlockingQueue（无界） 串行执行，适合日志、顺序任务；单线程易成瓶颈，队列同样无界
newScheduledThreadPool(n) 固定 n（maximumPoolSize 无效） DelayedWorkQueue 支持定时与周期任务；队列无界，任务积压同样会 OOM

四者的默认拒绝策略都是 AbortPolicy，但拒绝只在“队列满且线程数已达上限”时才触发：其中三种队列无界、永远不满，CachedThreadPool 的队列容量为 0 而线程上限是 Integer.MAX_VALUE。所以几乎走不到拒绝，任务只会一直堆到 OOM。

应用

线程由线程池统一提供，不要自己 new Thread，也不要用 Executors。四种预设都没给队列或线程数设置合理上限，把风险留给了使用方；显式构造 ThreadPoolExecutor 后各项参数自己定，行为可预期，也便于按业务调优。

核心线程默认不回收。确实需要回收时调用 allowCoreThreadTimeOut(true)，此后核心线程也按 keepAliveTime 超时退出（需要 keepAliveTime > 0）。它和构造参数可以配合 Nacos 之类的配置中心，在运行时动态调整。

空闲线程的状态：默认阻塞在 workQueue.take() 上，处于 WAITING；开启核心线程超时后改走 poll(keepAliveTime)，处于 TIMED_WAITING。新任务入队时被唤醒，回到 RUNNABLE 执行。

按优先级执行：把 workQueue 换成 PriorityBlockingQueue，提交的任务需实现 Comparable 或由队列构造时传入 Comparator。注意它同样是无界队列，需要自己限容——例如继承后重写 offer()，超过阈值返回 false，此时线程池会转而尝试扩容，仍失败才走拒绝策略。
