高并发下的 redis 缓存策略 - 2

超卖问题与一人一单

美团后台开发 - 暑期实习, 一面.

美的后端开发工程师-JAVA/中国区域 - 秋招, 一面.

以优惠券抢购为例。规则：一共 N 张，限时开抢，一人一张，抢完为止。

为什么会超卖

最直观的实现：

  1. 查这个用户是否已有订单，有就报错；
  2. 查库存，为 0 就报错；
  3. 扣库存、写订单，返回成功。

问题出在 2 和 3 之间。查询和修改是两条独立语句，中间没有锁，这就是典型的 check-then-act：库存只剩 1 时，A、B 两个线程都查到“还有 1 张”，都判断通过，然后各自扣减——库存变成 -1，两个人拿到了同一张券。并发越高，挤进这个空档的线程越多，超卖越严重。

悲观锁：正确但慢

把 2、3 包进互斥锁，同一时刻只放一个线程进。正确，但代价大：抢购瞬间几万请求，一次只放一个，其余全部排队；排队期间既占着 Tomcat 线程，也占着数据库连接。RT 直接雪崩。

悲观锁 乐观锁
对冲突的假设 一定会冲突，先加锁 很少冲突，不加锁
做法 进临界区前 lock 写入时确认“我算的数据没被人改过”
冲突时 阻塞等待 校验失败，重试或报错
适合 写多、冲突频繁 读多写少、冲突稀少

CAS 与 ABA

CAS（Compare And Swap）是最典型的乐观锁：写入时比较“当前值”是否等于“我读到的值”，相等才写入。

但直接比值会踩 ABA：库存 1 → 被 B 抢走变成 0 → C 退单又变回 1。A 校验时看到还是 1，以为没人动过，成功扣减。值回到了原样，中间却发生过变化。

修正办法是比版本号：每次写入 version + 1，只增不减，永远不会回到旧值。

高并发下 CAS 还有个先天缺陷：失败率高，线程不断重试，白白烧 CPU。所以要么限制重试次数（超了就直接失败或退化成加锁），要么干脆不自己写，把判断交给数据库。

一人一单

只在代码里 if 判一下，和超卖是同一个毛病。两道防线：

层次 手段 作用
减少无效请求 Redis SET user:1:coupon:5 1 NX EX 60 抢到标记的才去访问数据库；过期时间防止请求异常时永久占位
最终兜底 唯一索引 UNIQUE (user_id, coupon_id) 重复插入直接报键冲突，任何并发路径都绕不过

前者是性能优化，后者才是正确性保证。只做前者，锁失效或 Redis 抖动时照样会出双单。

再往前一步：库存也预扣在 Redis。真正的秒杀不会让几万请求打到 MySQL，而是在 Redis 里把库存减成负数就直接挡掉：

GET 和 DECR 放在同一段 Lua 里，Redis 执行脚本期间不插别的命令，扣减不会被打断。返回 1 才去同步数据库下的单，数据库那边再用 stock > 0 与唯一索引做最终确认。

另一种思路是双写 + 对账：请求同时落到 Redis 和数据库，两边都做原子扣减；数据库作为唯一真相源，后台线程或定时任务比对两边的库存，不一致就以库为准修复。一致性更强，但可用性更差——任一边故障都会让扣减卡住。只有数据库本身做了分库分表、写入能力足够时才值得这么做。

请求量再往上，入口还得限流——计数器、令牌桶、漏桶都行，把绝大多数请求挡在 Redis 之前。

持久化

腾讯混元 - 实习, 一面.

持久化有两种方式：RDB（Redis Database）存某一刻的全量数据，AOF（Append Only File）记执行过的每一条写命令。两者可以同时开。

RDB AOF
存什么 全量快照，二进制 写命令日志，文本
文件大小 小 大，且持续增长，需要重写
恢复速度 快，直接读回 慢，要把命令重放一遍
会丢多少 两次快照之间的全部写入 最多 1 秒（everysec）
写盘方式 fork 子进程，主进程基本不受影响 刷盘在主线程，重写时 fork 子进程

RDB

把某一时刻的全部数据序列化进 dump.rdb，重启时直接读回内存。

触发方式 说明
SAVE 主线程同步写盘，期间拒绝所有请求，只在运维手动操作时用
BGSAVE fork 子进程写盘，主线程继续服务
配置 save <秒> <次数> 例如 save 900 1：900 秒内至少 1 次写就自动 BGSAVE
主从全量同步 从节点首次连上主节点，主节点自动 BGSAVE 生成 RDB 再发过去
SHUTDOWN 未开 AOF 时，关闭前会保存一次

fork 时子进程和父进程共享内存页（写时复制），所以 BGSAVE 不会立刻让内存翻倍。但写操作多时，被改过的页要复制，内存占用仍可能接近翻倍——这也是 maxmemory 要留余量的原因。

AOF

appendonly yes 开启。一条写命令不是一步落盘的，要过三步：

  1. append：命令追加到 AOF 缓冲区 server.aof_buf；
  2. write：调用 write() 交给内核页缓存，此时断电仍会丢；
  3. fsync：调用 fsync() 真正刷到磁盘，这一步最慢。

appendfsync 决定第 3 步的时机：

策略 刷盘时机 最多丢 代价
always 每条命令都 fsync 0 吞吐骤降
everysec 每秒一次，后台线程做 约 1 秒 默认值，够用
no 交给操作系统 最多约 30 秒 最快，不可控

重写

触发方式：手动 BGREWRITEAOF，或自动触发，需同时满足：

percentage 设为 0 则关闭自动重写。

为什么需要重写：日志只追不改，SET k 1 之后 SET k 2 两条都在，但只有后一条有用。重写就是按当前内存状态重新生成最精简的命令集。

重写期间发生了什么：

  1. 主进程 fork 子进程，子进程按 fork 那一刻的内存快照写新文件，完全不读旧 AOF；
  2. 子进程写盘期间，新来的写命令既要追加到旧 AOF 缓冲，还要额外追加一份到 AOF 重写缓冲区 aof_rewrite_buf；
  3. 子进程写完，主进程把 aof_rewrite_buf 的内容补到新文件末尾；
  4. rename() 原子替换旧文件。

所以不会重复：旧文件里的命令一条都不会搬进新文件，新文件只多出“快照之后新产生的命令”。第 3 步追加缓冲时主进程要阻塞，这是重写的主要开销。

混合持久化

aof-use-rdb-preamble yes（Redis 7.0 起默认开启）。

AOF 文件变成前半段 RDB 快照 + 后半段增量 AOF 命令。重写时子进程直接按 RDB 格式写快照，比逐条生成命令快得多，文件也小。

加载时先读 RDB 头恢复全量，再重放后面的 AOF 命令，所以恢复速度接近纯 RDB，丢数据风险又和 AOF 一样低。代价是文件不再是纯文本，cat 不出来了。

断电导致 AOF 末尾只有半条命令时，aof-load-truncated yes（默认）会截断、告警，然后正常启动；设为 no 则直接拒绝启动。要保数据就设 no，要保可用性就保持默认。

数据能丢吗 建议
缓存、会话这类丢了能重建 只开 RDB，省 CPU 也省磁盘
有一定价值 RDB + AOF 都开，或开混合持久化
不能丢 AOF appendfsync always + 主从 + 定期 RDB 备份

生产上至少开 RDB：它既能当备份，重启也比纯 AOF 快。只开 AOF 的话，AOF 本身损坏时没有第二份数据可回退。

内存管理

先确认占了多少

重点看两个值：used_memory 是分配器看到的已用内存，used_memory_rss 是操作系统看到的实际驻留内存。两者比值 mem_fragmentation_ratio 明显大于 1 说明碎片多；小于 1 说明部分内存被换到了 swap——这会让 Redis 变得极慢，要警惕。

设置上限

maxmemory 4gb。不设的话 Redis 会一直吃内存，直到被 OOM Killer 杀掉。

注意 maxmemory 只管数据，不含 fork 时的写时复制、主从复制缓冲区、内存碎片。所以一般按物理内存的 60%~75% 设；同机部署其他服务时要留更多。打满且策略为 noeviction 时，写命令直接返回 OOM 错误。
