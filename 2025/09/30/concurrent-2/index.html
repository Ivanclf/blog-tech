Java内存模型

Java内存模型（JMM）是一套规范，定义多线程环境下共享变量的访问规则：线程之间如何通过主内存交换数据，以及一个线程的写操作在什么条件下对另一个线程可见。

JMM 把内存抽象为主内存和工作内存：共享变量存放在主内存中，每个线程有自己的工作内存，保存它用到的共享变量副本。

  • 线程对共享变量的读写都在工作内存中进行，修改后不保证立刻写回主内存。
  • 线程读取共享变量时，也不保证能读到其他线程刚写入的值。

什么时候写回、什么时候重新读取，由 JMM 的 happens-before 规则约束：只有经过 volatile 写、解锁等同步动作，副本与主内存之间才强制同步。

需要注意的是，主内存与工作内存是抽象概念，并不严格对应硬件的 RAM 与 CPU 缓存，而是涵盖了寄存器、各级缓存、写缓冲区以及编译器优化后的存储。这套抽象的意义在于屏蔽不同硬件平台的内存差异，让程序在任何平台上都具备一致的可见性语义，而不是为了“减少访问 RAM 的开销”。

JMM 主要关注以下三个方面：

  1. 原子性
    一个或多个操作要么全部完成，要么全部不生效。JMM 保证除 long、double 外的基本类型（以及引用类型）的单次读写是原子的；long、double 若不加 volatile，在 32 位 JVM 上可能被拆成两次 32 位操作（JLS 17.7 允许）。复合操作如 i++ 一定不原子。
  2. 可见性
    一个线程写入共享变量后，其他线程能否读到新值。普通变量不提供任何保证，需要借助 volatile、synchronized（解锁前刷新、加锁后重新读取）或 java.util.concurrent 中的工具类，而且这里的“可见”是指在 happens-before 关系成立之后，并非“立刻”。
  3. 有序性
    单线程内，程序看起来按代码顺序执行（as-if-serial）；多线程之间，只有在 happens-before 关系成立时才能依赖执行顺序，否则编译器和 CPU 都可以重排序。重排序分为三类：编译器重排序、指令级并行重排序、内存系统重排序。重排序会让双重检查锁定失效，需要给被检查的字段加 volatile 才能禁止。

最后注意区分两个概念：JVM 运行时数据区（堆、虚拟机栈、方法区等）是 JVM 运行时的物理内存分区；JMM 是并发语义层面的抽象，讨论的是线程与主内存之间的可见性与顺序，与具体分区并无对应关系。

Happens-Before 原则

happens-before 回答“谁的写，谁能看见”。A happens-before B（下称 A hb B）的确切含义是：A 的结果对 B 可见，同时 A 不会被重排到 B 之后。

JMM 定义了以下规则：

规则 内容
程序顺序 同一线程内，代码中靠前的操作 hb 靠后的操作
监视器锁 对同一把锁，unlock hb 后续的 lock
volatile 对同一变量，写 hb 后续的读
线程启动 start() hb 新线程中的任何操作
线程终止 线程中的任何操作 hb 其他线程检测到它结束（如 join() 返回）
线程中断 interrupt() hb 被中断线程检测到中断
默认初始化 对象的默认赋值（0、false、null）hb 程序中的其他所有操作
对象终结 构造函数结束 hb 该对象 finalize() 开始
传递性 A hb B 且 B hb C，则 A hb C

日常用得最多的是 volatile 和监视器锁这两条。配合传递性，它们可以把可见性“接力”下去：线程 A 解锁 → 线程 B 加同一把锁 → B 写 volatile 变量 → 线程 C 读该变量，于是 A 的所有操作对 C 都可见。

要留意：happens-before 是部分有序的。两条操作之间若不存在这条关系，它们的顺序就不确定，编译器和 CPU 可以任意重排。

as-if-serial 语义

单线程里，编译器和 CPU 可以随意重排、合并、删除指令，只要最终结果和按代码顺序执行一致。这个允诺就是 as-if-serial。

A、B 都只被 C 使用，依赖只有 A→C、B→C：

graph TD
    A((A)) --> C((C))
    B((B)) --> C

所以 C 必须排在 A、B 之后，而 A、B 之间没有依赖，可以互换。

两者的分工可以这样理解：as-if-serial 是发给编译器的一句承诺——“你只要保证单线程结果不变，随便优化”；happens-before 是对多线程的一条红线——优化不能破坏这条可见性关系。二者并不冲突：重排只要不越过 happens-before 就安全；一旦跨线程共享数据却没建立 happens-before，重排的后果就会暴露出来，结果变得不可预期。

volatile 关键字

volatile 只保证两件事：可见性和有序性，不保证原子性。

可见性：写 volatile 变量后立即刷新到主内存，读时强制从主内存重新取值，所以其他线程能看到最新值。

有序性：volatile 写之前的操作不能重排到它之后，volatile 读之后的操作不能重排到它之前。这也是双重检查锁定必须给实例字段加 volatile 的原因——否则 new 的“分配内存、初始化、赋引用”三步可能被重排，其他线程会拿到一个构造了一半的对象。

不保证原子性：i++ 是“读-改-写”三步，多线程并发仍会丢更新；需要原子性就用 synchronized、锁或 AtomicInteger。

用于引用类型时，只保证引用本身的可见（能看到指向最新对象），不保证对象内部字段的可见性——字段要么也声明 volatile，要么用锁保护。

实现上，JVM 靠在该变量的读写前后插入内存屏障来达到上述效果，x86 上通常对应一条带 lock 前缀的指令。

synchronized 关键字与 ReentrantLock

synchronized 是 JVM 内置的互斥手段，基于对象的监视器（Monitor）实现：进入同步代码前必须先拿到 monitor，退出时自动释放，不需要手写解锁。

锁谁

写法 锁对象
synchronized 实例方法 当前实例 this
synchronized 静态方法 该类的 Class 对象
synchronized (obj) { } 括号里的对象

所以两个不同实例的实例方法互不排斥，而静态方法在整个类范围内共用一把锁。

不建议锁谁

  • 构造方法：语法不允许加 synchronized；对象此时还没有发布出去，本来也不需要。
  • 字符串字面量、包装类：它们来自常量池或缓存，全局共享，不相干的代码可能锁到同一个对象，引发意外争用甚至死锁。
  • this 之外的公开对象：外部代码能拿到它，锁的边界就不可控了。

字节码层面

同步代码块被 monitorenter / monitorexit 包住（编译器会再补一条 monitorexit 覆盖异常路径）；同步方法不加指令，靠方法访问标志 ACC_SYNCHRONIZED 隐式加锁。锁状态记在对象头的 Mark Word 中，重量级锁时 Mark Word 存的是指向 ObjectMonitor 的指针。

提供了什么保证

保证 来源
互斥 同一时刻只有一个线程能进入 monitor
可见性 unlock hb lock：解锁前的写对之后加同一把锁的线程可见
有序性 同步块内外的指令不会被重排穿越块边界
可重入 同一线程可重复进入，计数递增；退出时递减，归零才真正释放，因此不会自己把自己卡死

重入计数在重量级锁中由 ObjectMonitor._recursions 维护，轻量级锁则由线程栈上的 Lock Record 记录。需要注意，synchronized 的锁本质上都是对象——每个对象关联一个 monitor，锁的是 monitor，而不是对象字段本身。

锁升级

JDK 6 引入锁升级：按竞争激烈程度，逐步从便宜的方案换到贵的方案。

状态 触发条件 做了什么 代价
无锁 对象刚创建 Mark Word 存 hashCode、GC 分代年龄、锁标志位 —
偏向锁（已弃用） 第一次有线程进入同步块 CAS 把该线程 ID 写进 Mark Word，标记“偏向它” 一次 CAS
轻量级锁 另一个线程来抢 撤销偏向，在争锁线程的栈帧中建 Lock Record，CAS 把 Mark Word 指向它；失败则自旋重试 若干次 CAS + 自旋
重量级锁 自旋仍拿不到锁 Mark Word 改指向 ObjectMonitor，抢不到的线程挂起进入 BLOCKED，等 OS 唤醒 两次内核态切换

几个容易记错的点：

  • 偏向锁只在旧版本存在。JDK 15（JEP 374）默认关闭，JDK 18 直接移除实现，所以现代 JVM 里只有无锁 → 轻量级 → 重量级这三态。它当年的价值在于：同一线程反复进出同步块时，只需比对 Mark Word 中的线程 ID，连 CAS 都不用。
  • 自旋是为了避免“为了一把很快就能拿到的锁去睡一觉”。线程挂起再唤醒要两次上下文切换，如果锁马上就能释放，自旋等待更划算；所以自旋次数是自适应的，由 JVM 根据历史成功率动态调整。
  • 升级后不会降级。同一次持锁过程中，锁状态只升不降；但锁释放后，对象可以回到无锁（或可偏向）状态，下次重新从低级别开始。

ReentrantLock

两者都是可重入锁，差别在于实现路线：synchronized 靠 JVM 的 Monitor，加解锁由字节码自动完成；ReentrantLock 靠 AQS 的一个 state 计数，lock() / unlock() 必须手写，且解锁一定要放在 finally 里。

ReentrantLock 换来了四种 synchronized 做不到的能力：

能力 用法 使用场景
可中断等待 lockInterruptibly() 等待时能被 interrupt() 唤醒并抛 InterruptedException，不必死等
超时放弃 tryLock(timeout, unit) 拿不到锁就走降级逻辑，避免无限期挂住
公平锁 new ReentrantLock(true) 严格按请求顺序发放；吞吐通常低于非公平锁
多条件队列 newCondition() 一把锁挂多个等待队列，可按条件精确唤醒，比 notifyAll() 少惊动无关线程

重入的实现很直白：state 记录持有次数。state == 0 时 CAS 抢锁并置 1；同一线程再进就 state++；每次 unlock() 减 1，减到 0 才真正释放并唤醒后继线程。

注意 ReentrantLock 默认是非公平的，而且 synchronized 也是非公平的——“公平锁更安全”是个误解，公平只影响排队顺序，不影响正确性。

AQS

AQS（AbstractQueuedSynchronizer）是 JUC 里各类同步器的骨架，ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 都建在它上面。它把“怎么排队、怎么阻塞、怎么唤醒”写好，子类只需回答一个问题：当前状态下，能不能拿到资源。

它只有两个核心构件：

  • volatile int state：同步状态，具体含义由子类定义。ReentrantLock 用它记重入次数，Semaphore 用它记剩余许可，CountDownLatch 用它记剩余计数。
  • 一个 CLH 变体的双向 FIFO 队列：抢不到资源的线程包装成 Node 入队，然后 park 阻塞；队首的后继线程在资源释放时被 unpark 唤醒。用双向队列是为了方便取消和超时时把节点从中间摘掉。

两种模式，对应两套方法：

模式 模板方法 子类需实现 例子
独占 acquire / release tryAcquire / tryRelease ReentrantLock
共享 acquireShared / releaseShared tryAcquireShared / tryReleaseShared Semaphore、CountDownLatch

这里用的是模板方法模式：acquire() 这类方法是 final 的，负责“先试 tryAcquire，失败就入队阻塞、等待被唤醒后重试”这一整套流程；子类只覆盖 tryXxx()，决定 state 怎么变。所以自定义同步器时不要重写 acquire，而是实现 tryAcquire。

虚拟线程

JDK 19 预览（JEP 425），JDK 21 正式（JEP 444）。

一句话：由 JVM 实现、由 JVM 调度的轻量级线程。它跑在平台线程上，平台线程再跑在 OS 线程上，所以是两层映射：

层次 谁调度 数量级
虚拟线程 JVM 数十万到上百万
平台线程（也叫载体线程，carrier thread） OS 几百到几千

为什么能撑住这么多线程

关键是卸载。虚拟线程碰到 IO、sleep、park 这类会阻塞的操作时，JVM 把它从载体线程上摘下来，载体线程立刻去跑别的虚拟线程；等 IO 就绪再把虚拟线程挂回去继续跑。

这就是它和平台线程的本质差别：平台线程一阻塞，就真白占一个 OS 线程；虚拟线程阻塞时“让出座位”，线程总数因此不再受 OS 线程数限制。

反过来，纯计算不会触发卸载——虚拟线程一直占着载体线程，此时它只是个更贵的普通线程。这是它不适合计算密集型任务的根本原因。

适用与不适用

场景 结论 原因
高并发 IO（HTTP 调用、DB 查询、文件读写），如网关、爬虫、服务聚合 适合 瓶颈在等待不在 CPU，阻塞时能卸载，少量载体线程就能撑住几十万并发
计算密集型（加解密、压缩、图像处理） 不适合 不阻塞就不卸载，只是多一层调度开销
依赖线程池复用或 ThreadLocal 缓存线程的老库 需谨慎 虚拟线程一个任务一个、用完即弃，这些假设不再成立

它也不改变编程模型：可以像写阻塞代码一样写，不必把逻辑拆成回调和 CompletableFuture 链——这才是“简化异步编程”的含义。

还有一个历史包袱：JDK 21~23 中，在 synchronized 块里阻塞会把载体线程一起钉住（pinning），JDK 24（JEP 491）起已修复。
