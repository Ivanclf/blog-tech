数据库底层 - 1

语句执行顺序

SQL 的书写顺序和执行顺序并不一致，实际按下面的顺序执行：

  1. from / join：先确定数据从哪些表来，把关联的表拼起来
  2. where：按条件过滤行
  3. group by：分组，聚合函数在这一步计算
  4. having：过滤分组后的结果
  5. select：挑出最终要返回的列
  6. order by：排序
  7. limit：截断返回的行数

顺序记牢了，两个容易踩的坑也就顺带解释清楚了：

  • where 里不能用 select 中定义的别名——那时还没执行到 select；order by 可以，因为它在 select 之后。
  • where 里不能写聚合函数，having 可以，因为聚合结果到 group by 才产生。

表结构

InnoDB 用 B+ 树组织数据，磁盘上按「段 → 区 → 页 → 行」逐层划分：

层级 说明
行 数据存储的最小逻辑单元，即一条记录
页 磁盘与内存交互的最小单位，默认 16 KB
区 64 个连续的页，约 1 MB；让页在物理上连续，把随机 IO 变成顺序 IO，也减少磁盘碎片
段 一个表或索引的逻辑存储容器，由若干区组成；区之间不要求物理连续

行里除了各列的值，还有 InnoDB 偷偷加的几个隐藏字段：

  • DB_TRX_ID（6 字节）：最近一次修改该行的事务 ID，MVCC 和锁判断都靠它。
  • DB_ROLL_PTR（7 字节）：指向 Undo Log 里的旧版本，用于回滚和快照读。
  • DB_ROW_ID（6 字节）：仅当表既没有主键、也没有唯一非空索引时才会生成，此时它充当聚簇索引的键。

每个索引对应两个段：叶子节点段（数据段）和非叶子节点段（索引段）。

数据页内部由 7 部分组成：

部分 作用
文件头 页号、上一页 / 下一页页号、校验和等
页头 页内记录数、空闲空间位置、最大事务 ID 等
最小 / 最大记录 两条虚拟记录 Infimum / Supremum，充当页内记录链表的头尾
用户记录 真正存的行数据，按主键顺序组成单向链表
空闲空间 页内还没分配的空间
页目录 把记录分组后做稀疏索引，支持页内二分查找
文件尾 校验和，用于判断这个页是否完整写入磁盘

文件头里的上一页 / 下一页指针把所有数据页串成一个双向链表，所以范围扫描可以顺着叶子节点一路顺序读下去。

MySQL 架构

MySQL 分两层：Server 层负责解析、优化、调度，存储引擎层负责真正存取数据。

组件 职责
连接器 建立连接、认证身份、加载权限
查询缓存 命中完全相同的 SQL 就直接返回；8.0 已移除
分析器 词法分析 + 语法分析，判断语句是否合法、涉及哪些表列
优化器 生成执行计划：选索引、定 join 顺序、改写子查询
执行器 按计划调用引擎接口逐行取数，并做 Server 层过滤
引擎层 真正读写数据，一般是 InnoDB（早期默认 MyISAM）

select 的执行过程

以 select * from t where id = 1 为例：

  1. 连接器：握手后校验账号、密码、host 权限，认证通过把权限读进连接对象。之后管理员再改权限，这条连接也不受影响，必须重连才生效。
  2. 查询缓存（仅 8.0 之前）：拿整条 SQL 文本当 key 查一次。
  3. 分析器：词法分析切出 select、表 t、列 id，语法分析检查语句结构。表或列不存在在这里就报错。
  4. 优化器：决定用哪个索引、多表 join 的驱动顺序、要不要把子查询改写成 join、能不能只读二级索引不回表。
  5. 执行器：校验表权限，然后循环调用引擎的”取下一行”接口，逐行判断 id = 1 是否成立，成立就放进结果集，直到取完。

update 的执行过程

update 的前半段（连接、解析、优化）和 select 一样，麻烦的是执行阶段：既要能回滚、能崩溃恢复，还要和 binlog 保持一致。以 update t set c = c + 1 where id = 1 为例：

阶段 做什么
1. 定位加锁 从 Buffer Pool 找数据页，不在就从 .ibd 加载；沿 B+ 树找到目标行，加排他锁（X 锁）
2. 记 undo 把修改前的旧值写入 Undo Log，供事务回滚和 MVCC 快照读使用
3. 改内存页 直接在 Buffer Pool 里改值，此时内存与磁盘不一致，该页成为脏页
4. 记 redo 把「哪个页的哪个偏移处改成了什么」写入 Redo Log Buffer，供崩溃后重放
5. 两阶段提交 redo 刷盘并标 prepare → Server 层写 binlog 并刷盘 → redo 标 commit
6. 异步刷盘 返回客户端成功；脏页由后台线程择机刷回 .ibd，不必等提交

第 5 步为什么要拆成 prepare 和 commit 两次：redo log 与 binlog 分属 InnoDB 和 Server 层，无法一次原子落盘，只能靠 XID 在崩溃后「对账」，保证两者要么都生效、要么都回滚。细节见下文 日志。

第 6 步之所以能异步刷盘，是因为 redo log 已经落盘兜底：此刻宕机也能重放恢复，不必在提交时做慢速的磁盘随机写。

InnoDB 内存结构

内存分四块，前两块决定读写性能：

组件 作用
Buffer Pool 缓存数据页和索引页，读写都先落在内存里，减少磁盘 IO
Log Buffer 缓存 redo log，攒够一批再顺序刷盘，减少随机写
Change Buffer 缓存对非唯一二级索引的写，等该页被读入时再合并
自适应哈希索引 为热点等值查询在内存里建哈希索引，由 InnoDB 自动开关

Buffer Pool

读：先查 Buffer Pool，命中直接返回；未命中就把整页从 .ibd 文件读进来。
写：直接改内存里的页，此时内存与磁盘不一致，该页称为脏页，由后台 page cleaner 线程择机刷回磁盘。

大小由 innodb_buffer_pool_size 控制。MySQL 8.0 默认只有 128 MB，生产环境一般设为物理内存的 50%~75%。这是影响 MySQL 性能最关键的单个参数。

Buffer Pool 缓存采用改造过的LRU算法。朴素 LRU 有个致命问题：一次全表扫描会把大量页读进来，把真正的热点全挤出去，即缓存污染。InnoDB 的做法是把这条 LRU 链表切成两段：

  • young（约 63%）：热点区，靠近链表头
  • old（约 37%）：冷区，靠近链表尾

新页一律先插到 old 头部（即 midpoint 指针处），而不是链头。想晋升到 young 头部必须同时满足两个条件：再次被访问，且已在 old 区停留超过 innodb_old_blocks_time（默认 1000 ms）。全表扫描时每页基本只读一次、间隔又短，两个条件都不满足，于是进不了热点区，真正的业务数据就不会被冲掉。淘汰时从 old 尾部开始踢。

young 内部还有一层惰性：页在 young 里的位置只有落在距头部 1/4 之后（即链表中后 3/4 段）才被移到头部，避免链表节点被频繁挪动。

相关参数：innodb_old_blocks_pct（old 区占比，默认 37）、innodb_old_blocks_time（晋升观察时间，默认 1000 ms）。

日志

MySQL 的日志按职责分三类，其余（错误日志、慢查询日志）只用于排查问题，不参与事务：

日志 归属 解决什么
binlog Server 层，所有引擎共用 主从复制、数据备份恢复
redo log InnoDB 独有 崩溃恢复，保证持久性
undo log InnoDB 独有 事务回滚、MVCC 快照读

binlog

binlog 是逻辑日志：记的是「数据发生了什么改动」，不是页级别的物理变化。只要表数据被修改就会写，与用哪个引擎无关。

三种格式：

格式 记什么 特点
statement 原始 SQL 语句 体积小；但 now()、rand()、uuid() 这类函数主从各算一次，结果可能不同，导致主从不一致
row 每行改动前后各列的值 精确，复制安全，是 8.0 的默认格式；代价是日志体积大，同步和恢复更慢
mixed 自动二选一 可能引起不一致的语句用 row，其余用 statement

落盘时机由 sync_binlog 决定：

  • 0：只写进 OS page cache，落盘交给操作系统，宕机会丢日志。
  • 1：每次提交都 fsync，最安全，默认值。
  • N：每提交 N 次 fsync 一次，在性能和安全性之间折中。

redo log

redo log 让 InnoDB 有了崩溃恢复能力，并保证事务的持久性。它把「随机写数据页」换成「顺序写日志」，这就是 WAL（Write-Ahead Logging）。

一次更新实际发生的事：

  1. 在 Buffer Pool 中修改数据页 → 产生脏页
  2. 把「哪个页的哪个偏移处改成了什么」写入 redo log buffer
  3. 在合适的时机把 redo log buffer 刷到 redo log 文件
  4. 脏页由后台线程慢慢刷回 .ibd 文件

第 3 步一旦完成，即使脏页还没落盘就宕机，重启后重放日志也能还原——这是持久性的真正来源，也是第 4 步能延迟、能合并的原因。

崩溃恢复：重启后先重放 redo log。有 commit 标记的事务重做；只有 prepare 且 binlog 里找不到对应 XID 的，说明事务没真正提交，按 undo log 回滚。

环形写入：redo log 文件组大小固定，日志在其中循环覆盖。两个指针划分空间：

  • write pos：当前写入位置
  • checkpoint：可被覆盖的起点，即它之前的日志对应的脏页都已落盘

想推进 checkpoint 必须先刷脏页——日志一旦被覆盖，那些还没落盘的数据页就再也恢复不了了。

主要参数：

参数 作用
innodb_flush_log_at_trx_commit 提交时的刷盘策略，见下表
innodb_redo_log_capacity 8.0.30+ 的日志总容量，此时文件数固定为 32 个
innodb_log_file_size / innodb_log_files_in_group 旧版本的容量控制方式，8.0.30 起被上一项取代
innodb_log_buffer_size redo log buffer 大小

innodb_flush_log_at_trx_commit 三档：

值 提交时做什么 宕机损失
0 什么都不做，全靠后台每秒刷一次 可能丢近 1 秒事务；性能最高
1 写入磁盘并 fsync 不丢；性能最低，默认值
2 写入 OS page cache，每秒 fsync MySQL 进程崩了不丢，整机断电会丢近 1 秒

redo log 让 InnoDB 能崩溃恢复，binlog 保证集群间的数据一致。

每个事务提交时分配一个 XID，并在 binlog 末尾追加 XID_EVENT。两阶段提交崩溃后，靠「redo 里的 XID」和「binlog 里的 XID」是否对得上，来决定提交还是回滚。

undo log

事务的每次修改都会在 undo log 里留一条撤销记录：insert 记一条删除，update 记被覆盖的旧值。它有两个用途：

  • 回滚：事务失败或手动 rollback 时，顺着记录反向执行，数据回到事务开始前的状态。
  • MVCC：其他事务做快照读时，顺着 undo 链找到该行对自己可见的旧版本。这也是 Undo 记录不能立刻删、要等没有事务再需要它才能清理的原因。

索引

索引是用空间换时间：把「找到某一行」从扫全表的 O(N) 降到几次页 IO。代价是额外占用存储，而且每次增删改都要同步维护索引，写越多越吃亏。

什么时候用不上索引

原因 例子 为什么
模式以通配符开头 like '%abc' B+ 树只按前缀有序，开头不定就无法定位起点
在索引列上做运算或函数 where id + 1 = 10、where date(created) = '2025-01-01' 索引存的是列的原值，算完的表达式没有索引可用
隐式类型转换 phone 是 varchar，却写 where phone = 13800000000 等价于 cast(phone as signed) = ...，变成了对列做函数
不满足最左前缀 索引 (a, b)，只按 b 查 树先按 a 排序，a 不确定时 b 在全局无序
范围条件之后的列 索引 (a, b)，where a > 1 and b = 2 a 走范围扫描后，剩余数据里 b 已不保证有序
要回表的行太多 条件命中全表 20% 以上 走索引要逐行回表（随机 IO），不如直接顺序扫全表
or 连接了非索引列 where idx_col = 1 or other_col = 2 另一半只能全表扫，整体就退化成全表扫

!=、not in、is null 不一定失效，取决于命中比例和优化器的代价估算。

底层结构

主流数据库和文件系统都用 B+ 树：

  • 哈希：等值查找 O(1)，最快。但哈希后完全无序，范围查询、排序、最左前缀一个都做不了。所以它只作为补充存在（如 InnoDB 的自适应哈希索引）。
  • 二叉搜索树 / AVL / 红黑树：每个节点最多 2 个子节点，N 条数据的树高约 $\log_2 N$。百万行就是 20 层，每下探一层基本一次磁盘 IO，20 次 IO 太慢。磁盘检索的成本由树高决定，所以正确方向是让每个节点尽量多装 key，而不是纠结平衡——这就是 B 树的思路。

B+ 树在 B 树的基础上又改了两点：

B 树 B+ 树
数据放哪 所有节点都存 key + 数据 只有叶子节点存数据，内部节点只存 key 和页号
单节点容量 数据挤占了空间，能放的 key 少 只放 key + 指针，扇出大得多，树更矮
查询路径 命中就返回，可能停在任意一层 一定走到叶子，所有查询路径等长
范围查询 要在树上中序遍历，反复上下跳 叶子节点间有双向链表，顺着走即可

在 InnoDB 里算一下（页 16 KB，主键 bigint）：

  • 非叶子页的每条索引项 = 8 字节 key + 6 字节页号 = 14 字节，一页约 $16384 / 14 \approx 1170$ 条，即每个内部节点扇出约 1170。
  • 叶子页假设一行 1 KB，一页约 16 行。

三层 B+ 树（根 → 中间层 → 叶子）能存 $1170 \times 1170 \times 16 \approx 2190$ 万行，这就是常说的「三层撑两千万」。查任意一行最多经过 3 个页，而根和中间层基本常驻 Buffer Pool，实际磁盘 IO 往往只有 1 次。

$$
\text{最大记录数} = \text{扇出}^{\text{树高}-1} \times \text{叶子节点容量}
$$

查找复杂度为 $O(\log_m N)$，$m$ 是扇出。因为 $m$ 很大（上千），这个对数远比 $\log_2 N$ 小。

索引的分类

按不同角度可以分成几组：

角度 类别 说明
是否存完整数据 聚簇 / 非聚簇 InnoDB 的主键索引是聚簇索引，其余都是非聚簇
约束强度 主键 / 唯一 / 普通 主键 = 唯一 + 非空，且一张表只能有一个
列数 单列 / 联合 联合索引要遵守最左前缀
索引内容 完整值 / 前缀 text、blob 只能建前缀索引
检索方式 B+ 树 / 全文 / 哈希 等值用 B+ 树或哈希，中文分词检索用全文
索引项密度 稠密 / 稀疏 InnoDB 只有稠密索引，稀疏见于搜索引擎

主键索引。建主键时 MySQL 会同时建对应的唯一索引。如果 create table 没写主键，InnoDB 会按顺序找替代：

  1. 有某个唯一索引且列都 not null → 拿它当主键；
  2. 都没有 → 生成一个 6 字节的隐藏列 DB_ROW_ID 当主键。

所以「没主键」的表并不是真的没有聚簇索引，只是一个你无法查询的隐藏键。

自增 id 为什么不连续？ 自增值是语句级分配的：insert 一开始就预领了 id，之后失败回滚也不会退回。所以回滚、插入失败、批量插入部分失败、手动指定 id 都会留下空洞。这属于正常现象，别指望自增 id 连续。

MySQL 5.7 之前自增值只存内存，重启后要重新扫描表尾部恢复；现在每次变更都会写进 redo log，并定期持久化到数据字典 mysql.ibd。

可选的具体类型。除了主键索引，InnoDB 常用的几种：

类型 语法要点 适用场景
唯一索引 unique key 业务上需要保证不重复，如手机号、订单号。允许多行为 null（null 之间不算重复）
普通索引 index / key 只加速查询、不做约束，绝大多数场景用这个
前缀索引 index(col(10)) 长字符串只索引前 N 个字符；text、blob 必须用前缀
全文索引 fulltext(col) + match ... against 文章内容检索。InnoDB 从 5.6 起支持
哈希索引 引擎自动（自适应哈希） 只支持等值查询，不支持范围和排序，由 InnoDB 自己判断是否启用

全文索引注意两点：默认按相关度（relevance）降序返回，不是按时间；中文必须先分词，建索引时要写 with parser ngram，否则会被当成一整串字符，查不到东西。against 的布尔模式下，+ 表示必须包含、- 表示排除、* 表示通配。

稠密索引与稀疏索引。按「每条数据是否都有一条索引项」区分：

  • 稠密索引：每个搜索键值都有自己的索引项。InnoDB 的 B+ 树索引就是这一类。
  • 稀疏索引：只为部分键值建索引项，靠区间定位。例如 gender 只有 M/F/U 三种取值，稀疏索引三条就够，体积能小一个数量级。InnoDB 没有这种索引，常见于 ES 等搜索引擎。

聚簇索引与回表

聚簇索引：索引的叶子节点直接存整行数据，索引即数据。InnoDB 的主键索引就是它。好处是主键查询一次 B+ 树就拿到全部列，范围扫描也是顺序读。

代价来自「数据必须按主键有序存放」：

  • 主键更新 → 行要挪位置，可能触发页分裂；
  • 用 UUID、随机字符串当主键 → 插入位置随机，频繁页分裂，索引碎片多。

所以主键要短、有序、不变，自增 bigint 是默认最优解。

非聚簇索引（二级索引）：叶子节点只存「索引列的值 + 主键值」，不存完整行。所以要拿到其他列，必须拿主键再查一次聚簇索引——这就是回表，一次查询等于两棵 B+ 树。

围绕回表，有三项优化：

优化 做法 省了什么
覆盖索引 查询的列全在索引里，叶子节点已经够用 完全免回表
索引下推（ICP） 把 where 中能用索引判断的条件交给引擎，在索引上先过滤 减少回表行数
MRR 把待回表的主键排序后再批量读 把随机 IO 变成近似顺序 IO

覆盖索引最值得主动利用：select id, name from t where name = 'x' 配上 (name) 索引，name 从索引取、id 本来就在叶子节点里存着，全程不回表。

联合索引

底层仍是 B+ 树，只是排序键变成了多列：先按 score 排，score 相同时再按 name 排。叶子节点存「所有索引列的值 + 主键」。

于是有了最左前缀原则：没有第一列，就无法定位第二列的开始位置。索引 (a, b, c) 能支持 a / a,b / a,b,c 三种前缀，以及 a 上的范围扫描；但 b 单独查、b,c 组合查都用不上。

两条实践结论：

  • 等值条件放前面，范围条件放后面。一旦某列用了范围（>、<、between、like 'x%'），它后面的列就只能用来在索引里过滤（ICP），不能再缩小扫描范围。
  • 区分度低的列放后面。性别这类列单独建索引几乎没用（只能把数据二分），但和区分度高的列组成联合索引可以省一次回表。

隐式转换的方向决定索引是否失效。 规则是：MySQL 会把字符串转成数字，不会把数字转成字符串。

  • varchar_col = 123：列被转成数字比较，等价于 cast(varchar_col as signed) = 123，索引失效。
  • int_col = '123'：字符串被转成数字，列本身没被包裹，索引照常可用。

字符串转数字时，从开头取到第一个非数字字符为止：'123abc' → 123，'abc' → 0。这也解释了为什么 varchar 列存数字容易出意外的匹配结果。
