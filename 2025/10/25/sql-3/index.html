数据库底层 - 2

锁的类别

按锁的粒度分三层，粒度越大开销越小、并发越差：

粒度 锁什么 典型场景
全局锁 整个实例的所有库 全库备份
表锁（含意向锁） 一张表 表结构变更、没有索引条件的大批量 DML
行锁 索引上的一条记录或一段区间 正常的并发事务

InnoDB 的主角是行锁，另外两层都是为了配合它。

全局锁

flush tables with read lock，让整个实例进入只读：所有库所有表都不能写，连 create、alter 也会被阻塞。

它适合全库逻辑备份，但 InnoDB 通常不用。全局锁更多是给 MyISAM 这类不支持事务的引擎兜底。

表锁

表级锁有两种：表级 S/X 锁和意向锁。

lock tables t read / write 手动锁整张表，粒度粗、并发差，InnoDB 日常不推荐。它主要用于表结构变更，以及不支持事务的引擎。

意向锁是 InnoDB 自动加的表级标记，表示「本事务打算在表里某些行上加锁」：

  • 要给行加 S 锁 → 先在表上加 IS（意向共享）
  • 要给行加 X 锁 → 先在表上加 IX（意向排他）

它解决一个具体问题：事务 A 想给整张表加写锁，得先确认表里有没有行锁。逐行检查不现实，于是让行锁持有者在表上留个标记——看到 IX / IS 就知道「有人在锁行」，直接拒绝即可。意向锁不锁任何数据，只用于快速判断冲突，这正是它存在的全部意义。

兼容矩阵（「是」表示可共存）：

已持有 / 请求 X S IX IS
X 否 否 否 否
S 否 是 否 是
IX 否 否 是 是
IS 否 是 是 是

三个读法：

  • X 与一切互斥。
  • S 与 S 兼容，但和 IX 冲突——因为 IX 意味着接下来要改行。
  • IX 与 IS、IX 与 IX 全部兼容。意向锁之间从不互斥，它们只是标记，不争数据。

另有 SIX（S + IX），表示「要读整张表、同时要改其中某些行」，与 X、S、SIX 都互斥。

行锁

行锁加在索引上，而不是数据行上。这一条决定了它的全部行为：定位不到索引就找不到行，行锁无从谈起。

另外先划清边界：普通 select 不加锁（快照读）。只有 select ... for update、select ... lock in share mode、update、delete、insert 才加锁。

按锁定范围分三种：

类型 锁什么 何时出现
记录锁 Record Lock 索引上的一条具体记录 唯一索引 / 主键等值查询且命中记录
间隙锁 Gap Lock 两条记录之间的空隙，不含记录本身 RR 下的范围查询，或等值查询没命中
临键锁 Next-Key Lock 记录本身 + 它前面的间隙，左开右闭 RR 下的默认形态

RR 下行锁默认就是临键锁：InnoDB 把索引切成 (prev, cur] 一段段，每段一把。唯一例外是「唯一索引等值且命中」，此时精确到一条记录，降级为记录锁——反正唯一值不会再有第二个，没必要锁间隙。

间隙锁唯一的目的就是防幻读：它不让别的事务往这个空隙里插。两个反直觉的性质值得记住：

  • 间隙锁只和插入互斥，彼此之间完全兼容。多个事务可以对同一间隙同时加间隙锁，不会互相阻塞。
  • RC 隔离级别下没有间隙锁，只有记录锁。所以 RC 有幻读，RR 基本没有。

插入时加的是插入意向锁（Insert Intention Lock），一种特殊的间隙锁，表示「我要在这个间隙的某个位置插入」。位置不同的插入意向锁可以共存，但都必须等已有的间隙锁释放。

这也解释了经典死锁：事务 A、B 各持有一个间隙锁，接着都要往对方锁住的间隙里插 → 插入意向锁相互等待 → 死锁。间隙锁之间不冲突，却因此谁都不肯先放手。

事务

事务把多个操作打包成一个不可分割的整体。ACID 是它的四个保证：

特性 保证什么 靠什么实现
原子性 Atomicity 要么全做，要么全不做 undo log 回滚
一致性 Consistency 事务前后数据都满足约束（转账前后总金额不变） 约束校验 + 业务代码，数据库只保证 A、I、D
隔离性 Isolation 并发事务互不干扰 锁 + MVCC
持久性 Durability 提交后就永久生效 redo log

隔离级别

腾讯微信支付 - 实习, 一面.

并发事务可能读到不该读的数据，有三种典型问题：

问题 现象
脏读 读到别的事务未提交的数据。对方一回滚，这份数据根本不存在
不可重复读 同一事务内两次读同一行，值变了。期间有别的已提交事务改了它
幻读 同一事务内两次执行同一条件查询，第二次多出了行。期间有别的已提交事务插入了它

前两个是「同一行的值变了」，幻读是「满足条件的行集合变了」。一个针对已有行的修改，一个针对新增行。

SQL 标准用四种隔离级别来控制这些问题的发生：

隔离级别 脏读 不可重复读 幻读
读未提交 read uncommitted 会 会 会
读已提交 read committed 不会 会 会
可重复读 repeatable read 不会 不会 一般会，InnoDB 实际不会
可串行化 serializable 不会 不会 不会

三处容易记错的地方：

  • Oracle、SQL Server、PostgreSQL 默认都是读已提交，只有 MySQL InnoDB 默认是可重复读。
  • InnoDB 的可重复读没有幻读。标准中 RR 只锁住已读到的行，别人仍能插新行；InnoDB 额外用间隙锁 / 临键锁把「不存在的位置」也锁上了，快照读又只看事务开始时的版本，两条路都堵住了。
  • InnoDB 的可串行化是把普通 select 隐式变成 select ... lock in share mode，让读也加 S 锁、读写互相阻塞。并发度大幅下降，所以很少用。

两段锁协议（2PL）

隔离级别是「允许什么乱象」的定义，2PL 则是实现可串行化的经典锁协议：

  1. 加锁阶段：访问任何数据前，先拿到对应的锁。这个阶段只加锁、不解锁。
  2. 解锁阶段：一旦开始释放锁，就不能再申请任何新锁。

两个阶段泾渭分明，所以叫两段锁。它保证任何并发执行的结果，都等价于某个串行执行的结果（冲突可串行化）。

但基础 2PL 有个漏洞：可能死锁，而且可能级联回滚——事务 A 改了数据并释放锁，事务 B 读到后 A 又回滚，B 读的就是脏数据。工程实现普遍用严格两段锁（Strict 2PL）：所有锁都持有到事务提交或回滚才释放，两个问题一起解决。

MVCC

字节跳动, 中国交易与广告 - 实习, 一面

MVCC（Multi-Version Concurrency Control，多版本并发控制）让读不加锁也能读到一致的数据。核心思路是：不改数据、也不复制数据，而是让每行都留着历史版本，读的时候自己挑一个「该看到的那一版」。

两种读取方式：

快照读 当前读
谁在用 普通 select select ... for update / lock in share mode / update / delete / insert
读到什么 ReadView 判定可见的那个旧版本 最新版本，并加锁
阻塞吗 不加锁，读写互不阻塞 会等锁

实现靠三样东西：

  1. 行上的 DB_TRX_ID：最后修改这行的事务 id。
  2. 行上的 DB_ROLL_PTR：指向 undo log 里这条记录的上一版本。顺着它往回走，就串成一条版本链，越往前越旧。
  3. ReadView：读的那一刻，记下「哪些事务还活着」。

判断某个版本对自己是否可见，就比对版本链上的 DB_TRX_ID 和 ReadView：

  • 小于 ReadView 里的最小活跃事务 id → 早就提交了，可见。
  • 是自己改的 → 可见。
  • 落在活跃事务 id 集合里，或大于等于最大活跃 id → 事务当时还没提交，不可见，顺着 DB_ROLL_PTR 找上一版。

不同隔离级别的差别，只在于 ReadView 什么时候生成：

隔离级别 ReadView 生成时机 效果
读已提交 每条 select 都新建一个 总能读到最新已提交的数据，所以会不可重复读
可重复读 事务第一条 select 建一次，整个事务复用 整个事务看到同一份数据，不会不可重复读
读未提交 不用 ReadView，直接读最新 会脏读
可串行化 普通 select 被改成加锁读，走当前读 不靠 MVCC

Oracle 的多版本读一致性

Oracle 用同一套思路，但机制不同：靠回滚段（Undo Segment）而不是版本链指针。

  • 每个查询开始时取一个 SCN（系统变更号），相当于「看到哪个时间点」。
  • 读数据块时，若块上的版本晚于该 SCN，就从回滚段把这一块重建成 SCN 时刻的样子。
  • 行头记录着「最后修改它的事务」，据此判断要不要重建。

结果是读永不阻塞写、写也不阻塞读。Oracle 只提供两种隔离级别：读已提交（默认，每条语句一个 SCN）和可串行化（整个事务一个 SCN），没有「读未提交」和「可重复读」这两档。

高可用

单机数据库有两个绕不过去的瓶颈，对应两种手段：

手段 解决的问题 引入的代价
读写分离 读请求全压在一台机器上 主从延迟
分库分表 单库数据量、写入量的上限 不能 join、没有本地事务、ID 冲突

读写分离

字节跳动, 中国交易与广告 - 实习, 一面

主库只负责写，多个从库分担读。写请求和读请求分开，读的吞吐靠加从库横向扩展。

复制流程（从库主动拉，主库被动推）：

  1. 主库把变更写入 binlog 文件
  2. 从库的 IO 线程连上主库，报上自己消费到的位点，请求之后的日志
  3. 主库的 binlog dump 线程把日志推给从库
  4. 从库 IO 线程收到后写入 relay log（中继日志，落盘后位点才算提交）
  5. 从库的 SQL 线程读 relay log，在本地重放一遍

从库为什么需要两个线程？IO 线程只管收，SQL 线程只管重放，收和放解耦，主库不会被从库的执行速度拖住。SQL 线程默认单线程重放，一旦主库写入并发高，重放跟不上就形成延迟；5.7 起支持按组提交并行重放。

复制模式：

模式 主库何时认为提交成功 风险
异步（默认） 写完 binlog 就返回 主库宕机，未传到从库的事务丢失
半同步 至少一个从库确认收到 binlog（不要求执行完） 多一次网络往返，性能略降
组复制 MGR 组内多数派认证通过 配置和运维复杂度高

主从延迟的成因：从库机器弱于主库、大事务一次性回放、从库还背着大量读请求、级联复制层数多、跨机房网络抖动。

应对：

  • 写完立刻要读自己的场景（如注册后跳详情页），这类读强制走主库。
  • 半同步复制，缩小「主库已提交、从库还没有」的窗口。
  • 关键业务按 GTID 判断从库是否已追平，未追平则等待或降级。

分库分表

两个维度交叉出四种拆分方式：

分库 分表
垂直 按业务模块拆库：订单库、用户库、商品库 按列拆表：冷热字段分离，大字段挪到扩展表
水平 同一张表的数据按规则拆到多个库 同一张表的数据按规则拆到多张表
  • 垂直拆分解决「字段太宽、表太多」，本质是业务解耦，几乎不带来副作用。
  • 水平拆分解决「单表数据量太大」，才是通常说的分片（sharding），代价最大。

B+ 树长到 4 层、热数据装不进 Buffer Pool、DDL 和备份耗时不可接受时，就应该分表了。

分片算法：

算法 定位方式 适合 缺点
哈希取模 hash(key) % N 读写随机、分布均匀 改 N 就要动几乎所有数据
范围 按 key 区间划分 范围查询多、数据分布均匀 热点集中（按时间分片时最新段压力最大）
映射表 查表得到位置 规则任意调整，扩容灵活 多一次查询，映射表自身成单点

哈希取模的扩容问题，实践上用一致性哈希或成倍扩容（N → 2N，只需迁移一半）缓解。

工具：ShardingSphere-JDBC（客户端 jar，无额外进程）或 ShardingSphere-Proxy（独立服务，任何语言都能连）。

不停机扩容三个阶段：

  1. 双写：新库上线，应用同时写新旧库，读仍走旧库。用 MQ 做异步补偿，靠幂等防重复写入。
  2. 追平历史：全量迁移存量数据，同时订阅 binlog 增量追平；关键查询双读比对，校验一致。
  3. 灰度切读：读流量逐步切到新库，观察无异常后切完，再停双写、下线旧库。

分片的代价为：

  • 不能跨库 join，得在应用层拼装。
  • 跨库写没有本地事务，必须引入分布式事务。
  • 自增 id 会冲突，需要全局唯一 ID（雪花、号段、Redis）。
  • 跨库分页、排序、聚合要在内存里二次处理，深分页尤其痛。

变更数据捕获：Canal

阿里国际数字商业集团, AI 应用研发工程师 - 实习, 一面

Canal 是订阅 binlog 的中间件：把数据库的变更当成一条条事件流，推给缓存、搜索引擎、其他数据源等下游。这类做法统称 CDC（Change Data Capture，变更数据捕获）。

原理

把自己伪装成一个从库，具体为

  1. Canal 用 MySQL 从库的身份连上主库，发 COM_BINLOG_DUMP 协议报文，并报上自己要的起始位点。
  2. 主库像对待普通从库一样，起一个 dump 线程把 binlog 流推过来。主库完全不知道自己面对的是一个假从库。
  3. Canal 解析 binlog（row 格式最完整，会带上每行改动前后的列值），还原成结构化事件：表名 + 主键 + 变更类型 + 新旧列值。
  4. 消费者从 Canal 拉事件，ACK 后位点推进。位点定期持久化，宕机后可从这里续拉。

应用

场景 做什么
缓存一致性 订阅变更 → 删缓存 / 更新缓存，替代「业务写完顺手删」
搜索引擎同步 订单库变更同步进 ES，做多条件检索
异构数据同步 同步到 ClickHouse、Redis、另一个库，做分析或异构存储
数据审计 / 订阅 记录谁在什么时候改了哪一行

和读写分离的区别：从库是整库的完整副本，只能读；Canal 是变更事件流，可以只关注几张表、可以投递到任意下游，也不承担查询流量。

运维要点

宕机后只有两种结局：

  • 位点已持久化 → 重启后从上次位点续拉，增量照常。
  • binlog 已被 purge、位点找不到了 → 增量断链，只能重新全量。

避免走到第二条：binlog 保留 3~7 天（binlog_expire_logs_seconds，旧版本 expire_logs_days）、不手动 purge、位点存到持久存储（ZooKeeper / MySQL）、多实例做 HA。

还要注意主库 binlog_format 必须是 row，statement 格式拿不到行级明细，Canal 无法还原事件。
