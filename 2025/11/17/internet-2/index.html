计算机网络应用

HTTP

打开一个网页，整个过程会用到哪些协议？主要经过以下步骤：

  1. 在浏览器输入 URL。

  2. 浏览器通过 DNS 协议获取域名对应的 IP 地址。
    查询顺序通常是：浏览器 DNS 缓存 → hosts 文件 → 系统 DNS 缓存 → 递归查询。

    DNS 查询与响应默认使用 UDP、端口 53；当响应报文过大（超过一个 UDP 报文能承载的大小）或进行区域传送时，会改用 TCP。现在也常用 DoH（DNS over HTTPS）或 DoT（DNS over TLS）进行加密查询。

  3. 浏览器根据 IP 和端口（HTTP 80 / HTTPS 443）向服务器发起 TCP 连接（三次握手）。如果是局域网，还需要先通过 ARP 解析网关 MAC 地址。

  4. 如果是 HTTPS，先进行 TLS 握手（此时通过 SNI 把目标域名告诉服务器，服务器据此选择对应证书），之后才能发送加密的应用数据。

  5. 浏览器在 TCP 连接上发送 HTTP 请求报文。若多个域名指向同一 IP，服务器通过请求头中的 Host 区分虚拟主机，返回对应网站的内容。

  6. 服务器处理请求，返回 HTML 响应报文。

  7. 浏览器解析 HTML、构建 DOM 并渲染页面。期间根据解析到的 CSS、JS、图片等 URL 再次发起 HTTP 请求，直到页面完全加载。

    • 同一域名下，浏览器会并行建立多条连接（HTTP/1.1 通常 6 条左右）；HTTP/2 起改为在单条连接上多路复用。
    • CSS 是渲染阻塞资源，未下载完成前页面不会渲染；JS（未加 async/defer）还会阻塞 HTML 解析。

  8. 通信结束后服务器或浏览器可关闭连接。HTTP/1.1 默认保持长连接，通常会复用连接一段时间，空闲超时后才关闭。

HTTP header

User-Agent

请求头，携带设备、操作系统与浏览器的信息。以 Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/142.0.0.0 Safari/537.36 Edg/142.0.0.0 为例：

片段 含义
Mozilla/5.0 历史遗留的兼容标记，几乎所有浏览器都会写上
Windows NT 10.0; Win64; x64 系统为 Windows 10/11，64 位，架构为 x86-64
AppleWebKit/537.36 (KHTML, like Gecko) WebKit 渲染引擎及版本。Chromium 实际使用 Blink（WebKit 的分支），保留此标识仅为兼容
Chrome/142.0.0.0 Chrome 内核版本
Safari/537.36 兼容性填充，并非真的 Safari
Edg/142.0.0.0 Edge 浏览器及其版本

Cookie

Cookie 是浏览器端保存的一小段键值对数据。HTTP 本身无状态，连接关闭后服务端无法辨认同一用户，Cookie 正是把用户信息（或标识）留在客户端的手段。可用 JS 创建并设置过期时间等属性。

Cookie 与 Session 的区别可以概括为：Cookie 存钥匙，Session 存数据，服务端通常凭 Cookie 中的 ID 找到对应的 Session。

特性 Cookie Session
存储位置 客户端浏览器 服务端（内存、文件、数据库等）
存储内容 简单的键值对字符串 任意数据结构
安全性 较低，易被查看、篡改或窃取 较高，客户端只拿到一个 ID
生命周期 可设置长期有效 通常较短，如关闭浏览器后失效
存储容量 小，单个约 4KB，且每个域名有数量限制 大，受服务器资源限制
性能影响 每次请求都会携带，增加带宽 占用服务器内存
依赖关系 可独立使用 通常依赖 Cookie 传递 Session ID

Accept 类

请求头，声明客户端愿意接受的内容。

请求头 含义
Accept 可接受的响应媒体类型（MIME），对应响应头的 Content-Type
Accept-Charset 可接受的字符集
Accept-Encoding 可接受的编码/压缩方式，如 gzip、br
Accept-Language 可接受的语言及其优先级

q 表示权重，取值 0~1，默认 1，越大优先级越高。如 Accept-Language: zh,en-US;q=0.9,en;q=0.8,zh-CN;q=0.7,ja;q=0.6,en-GB;q=0.5，优先级依次为：中文 1.0 > 美式英语 0.9 > 通用英语 0.8 > 简体中文 0.7 > 日语 0.6 > 英式英语 0.5。

ETag 与 Last-Modified

二者都是响应头，由服务器在响应中给出，用来标记资源的版本，常被称为“缓存校验器”（validator）。客户端下次请求时通过 If-None-Match / If-Modified-Since 把它们带回服务器，由服务器判断资源是否已经变化。

响应头 示例 说明
ETag ETag: "33a64df5..." Entity Tag，服务器为某个版本的资源分配的唯一字符串。"..." 为强校验器，要求字节级完全一致；W/"..." 为弱校验器，允许语义等价
Last-Modified Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT 资源最后修改时间，精度只到秒

两者互补：ETag 更精确，能区分同一秒内的多次修改，但需要服务器额外计算；Last-Modified 实现简单，但精度有限，且文件拷贝、重新部署都可能更新其时间值，导致“时间变了但内容没变”。若资源经过压缩、转码，字节不同而语义相同，则更适合使用弱 ETag。

If 类

条件请求头：客户端在请求中附加前提条件，服务器只有条件满足时才执行操作。条件通常由上面两个校验器提供，例如 If-None-Match 比较 ETag，If-Modified-Since 比较 Last-Modified。

请求头 典型用途 条件满足 条件不满足 白话理解
If-Match 安全更新 / 删除 执行操作 412 Precondition Failed 我手里的版本号和服务器上的一致，才允许覆盖
If-None-Match 缓存验证 / 安全创建 GET 返回 304 Not Modified，其他方法返回 412 执行操作，返回新内容 本地缓存与服务器不一致（或资源不存在）时，才把新内容发给我
If-Modified-Since 条件获取缓存 返回 304 Not Modified 执行操作，返回新内容 文件在该时间点之后没被改过，就不用再传给我
If-Unmodified-Since 安全更新 执行操作 412 Precondition Failed 文件自上次下载后没人动过，才允许我更新
If-Range 断点续传（配合 Range 使用） 返回 206 Partial Content 返回 200 与完整资源 还是原来那个文件就接着传，否则整个重传

HTTPS

HTTPS 是 HTTP over TLS 的简称，其安全保障由 SSL/TLS 协议提供（早期为 SSL，现均为 TLS）。

特性 HTTP HTTPS
安全性 明文传输，不安全 加密传输，安全
协议 基于 TCP HTTP over TLS，底层通常是 TCP（HTTP/3 则基于 QUIC over UDP）
端口 80 443
工作方式 直接传输数据 先完成 TLS 握手，再传输加密数据
需要证书 否 是，由证书颁发机构（CA）签发
数据完整性 无法验证数据是否被篡改 可验证数据在传输过程中是否被篡改
SEO 浏览器标记“不安全”，对 SEO 略不利 浏览器显示安全锁，且是 SEO 排名因素之一

浏览器连接到服务器的 443 端口后，TLS 1.3 的握手（1-RTT）过程如下：

  1. Client Hello：客户端发送支持的版本、密码套件、随机数 Client Random、SNI，以及临时生成的 ECDHE 公钥（key_share）。
  2. Server Hello：服务器选定密码套件，返回随机数 Server Random 和自己的 ECDHE 公钥。双方用各自的私钥加对方的公钥，各自算出同一个共享密钥。
  3. 服务器发送加密的握手消息：包括证书链、CertificateVerify（用证书私钥对握手摘要签名，证明自己持有私钥）和 Finished（握手过程校验）。
  4. 客户端校验并回复：校验证书链、域名、有效期和签名，通过后发送自己的 Finished，双方据此派生会话密钥。
  5. 应用数据传输：之后的数据都用会话密钥对称加密。

完整握手需要 1-RTT。若客户端持有上次的会话票据（PSK），可走会话恢复，在 Client Hello 中就开始加密，实现 0-RTT；代价是 0-RTT 数据可能被重放，因此只适合幂等请求。

相比 TLS 1.2，TLS 1.3 主要变化为：只保留带前向保密的 ECDHE 与 PSK 两种密钥交换，废弃 RSA 密钥交换、CBC、RC4、SHA-1 和压缩；Server Hello 之后的消息全部加密；密钥派生统一使用 HKDF。

会话密钥采用对称加密（如 AES-GCM、ChaCha20-Poly1305），因为对称加密速度快、适合加密大量数据；非对称加密开销大，只用于身份认证和密钥交换。

HTTP 协议

HTTP 协议经历了四个阶段。

特性 HTTP/1.0 HTTP/1.1 HTTP/2.0 HTTP/3.0
连接方式 短连接 长连接，可管道化 一条连接多路复用 基于 QUIC 的多路复用
队头阻塞 应用层，请求串行 应用层，管道化下仍存在 应用层解决，但受 TCP 丢包影响 传输层解决
服务器推送 不支持 不支持 支持（主流浏览器已移除） 支持（同样已被移除）
传输协议 TCP TCP TCP UDP（QUIC）
加密 无要求 无要求 规范上非强制，浏览器实际只支持 over TLS 强制，内置 TLS 1.3
头部压缩 无 无 HPACK QPACK
连接建立 TCP 握手 TCP 握手 TCP + TLS 握手 QUIC 握手，可 0-RTT

HTTP/1.0 使用短连接：每个请求都要新建一次 TCP 连接，收到响应后立即关闭。建连开销大，且受浏览器对单域名并发连接数的限制，资源只能排队加载。

HTTP/1.1 改用长连接：默认保持 TCP 连接打开，可在同一连接上先后发送多个请求，并通过管道化（pipelining）连续发送。但响应必须按请求顺序返回，前一个响应慢仍会拖住后面的请求，即应用层队头阻塞。此外还有头部冗余：每个请求都携带大量重复头部，且不做压缩。

HTTP/1.1 还补充了大量状态码，如 100 Continue（服务器告知客户端可以继续发送请求体）、409 Conflict（请求与资源当前状态冲突）等。

HTTP/2 以二进制帧替代文本报文，在同一条 TCP 连接上并发多条流，每条流有唯一 ID；响应可以乱序返回，因此解决了 HTTP 层的队头阻塞；同时用 HPACK 压缩头部，并支持服务器推送（Server Push，但主流浏览器已移除该功能）。

它的瓶颈转移到 TCP 本身：TCP 按序交付，一旦某个包丢失，整条连接上的所有流都要停下来等重传。

HTTP/3 彻底更换底层传输协议，改用基于 UDP 的 QUIC，以解决 TCP 层的队头阻塞：

  • 各条流相互独立，某个流丢包只影响该流
  • 连接建立更快：首次 1-RTT，会话恢复可 0-RTT；而 TCP + TLS 1.3 需要 2 RTT，TLS 1.2 需要 3 RTT
  • 支持连接迁移：切换网络时 TCP 必须断开重连，QUIC 用连接 ID 标识会话，可以无缝迁移
  • 强制加密：TLS 1.3 内置于 QUIC

HTTP/1.0 到 HTTP/2 的切换在应用层协商。HTTP/1.1 默认使用长连接（Connection: keep-alive，已成为默认行为）。升级到 HTTP/2 主要有两种方式

  • 客户端在 TLS 握手时通过 ALPN 扩展告诉服务器自己支持 HTTP/2（实际部署中最常见）
  • 明文场景下，客户端发送含 Upgrade: h2c 的 HTTP/1.1 请求，服务器同意则返回 101 Switching Protocols，之后双方切换为 HTTP/2

HTTP/3 则通过响应头 Alt-Svc 或 HTTPS DNS 记录（HTTPS 记录）宣告自己支持 h3，客户端据此改用 QUIC 连接。

保存用户状态

HTTP 协议本身是无状态的，这意味着服务器默认情况下无法区分两个请求是否来自同一个用户，因此对于需要记住用户状态的业务，往往有以下几种机制

Session 配合 Cookie

URL 重写

浏览器禁用 Cookie 时，还可以将 SessionID 直接附加到 URL 的末尾，该方法使得 URL 变长，且安全性较低，容易被复制、分享或记录到日志中，还可能对 SEO 不太友好。

Token-Based 认证

JWT (JSON Web Tokens) 就是使用这种方法。该方法简化的步骤如下

  1. 用户向服务器发送用户名、密码及验证码用于登录系统
  2. 若校验正确，服务端会返回已签名的 Token，假如为 JWT
  3. 客户端收到 Token 后自己保存到浏览器的 LocalStorage
  4. 用户在此后每次向后端发送请求都在 header 中带上这个 JWT
  5. 服务器检查 JWT 并从中获取用户相关信息

IP

为了获取客户端真实 IP，通常可以采用以下方法

  • 应用层：通过 X-Forwarded-For 请求头获取，但这里的 IP 可能不是真实 IP。如果经过代理服务器，该字段可能会有多个值。并且，这种方法只适用于 HTTP 和 SMTP 协议
  • 传输层：利用 TCP Option 字段承载真实源 IP 信息。这需要通信双方都支持发送这种独特的 TCP 包
  • 网络层：隧道 + DSR 模式，但实施起来比较麻烦

DNS 只负责把域名解析成 IP，无法区分同一 IP 后面的多个站点，真正的区分发生在传输层之上：

层次 区分依据 说明
传输层 端口 IP:port 才能唯一确定一个监听套接字。不同服务监听不同端口（HTTP 80、HTTPS 443、SSH 22）天然分开；若都监听 80，则必须靠上层信息区分
HTTP Host 请求头 HTTP/1.1 起必须携带，值为目标域名。服务器（如 Nginx 的 server_name、Apache 的 VirtualHost）据此把请求路由到对应的虚拟主机。HTTP/2 与 HTTP/3 用 :authority 伪首部表达同样信息
HTTPS SNI TLS 握手时整个 HTTP 请求还是密文，服务器拿不到 Host，因此客户端在 Client Hello 中通过 SNI 扩展先告知目标域名，服务器据此选择对应证书，握手完成后再由 Host 路由
证书 SAN / 通配符 一张证书可通过 SAN 覆盖多个域名，或使用 *.example.com 通配符；这样即使客户端不支持 SNI，也不会因默认证书域名不匹配而报错
反向代理 / CDN Host 或 SNI 代理根据 Host（七层代理）或 SNI（四层透传）决定转发到哪个后端，多个站点共享同一个入口 IP

需要注意，Host 头由客户端提供，可以被伪造，服务端应只接受白名单内的域名（否则可能出现 Host Header Injection、缓存投毒等问题）；而 SNI 在 TLS 握手阶段以明文传输（TLS 1.3 默认也不加密），因此也会泄漏访问的域名，Encrypted Client Hello（ECH）正是为解决这一点而提出的。

同源策略

同源策略（Same-Origin Policy，SOP）是浏览器内置的安全边界：它规定一个源的脚本只能自由地读写同一个源下的资源，访问其他源时要受限制。

什么是“源”

“源”（origin）由协议、域名、端口三元组唯一确定，三者全部相同才算同源，缺一不可。

需要区分两个容易混淆的概念：源用于安全边界判定，站点（site，即可注册域 + 协议）用于 Cookie 的 SameSite 等判定。a.com 与 b.a.com 属于同一个站点，但不是同一个源。

限制的范围

同源策略的核心可以概括为：限制“读”，不限制“发”。跨源的请求可以发出，但脚本拿不到返回的数据。

行为 是否受限 说明
fetch / XMLHttpRequest 读取跨源响应体 受限 需目标服务器通过 CORS 显式放行才能读
读取跨源 <iframe> 内的 DOM 受限 只能操作自己的窗口，无法读取他人页面内容
读写 localStorage、IndexedDB、sessionStorage 受限 存储按源隔离，各自独立
用 <img>、<script>、<link>、<video> 加载跨源资源 不受限 请求正常发出，资源正常使用，但脚本无法读取其内容
用 <form> 向跨源地址提交 不受限 提交会真实发生，只是响应被送到目标页面而非当前页
加载跨源脚本后调用其暴露的全局变量 不受限 这正是 JSONP 的原理，也是 <script> 引入的风险所在
在页面间传递消息 受限 需通过 postMessage 显式通信，且接收方要校验 event.origin
设置或发送 Cookie 不受同源策略约束 由 Cookie 自身的 Domain、Path、SameSite 属性决定

之所以设计成“可以发、不能读”，是因为发起请求本身（如加载一张图片）无法造成信息泄漏，真正危险的是 A 站的脚本能读到 B 站的数据——比如用户在 B 站登录后的个人资料、私有邮件、接口返回的业务数据等。

关于 Cookie 需要特别注意：document.cookie 能读到哪些 Cookie，取决于 Domain 和 Path 属性，而不是同源判定。若把 Domain 设成 .a.com，那么 a.com、b.a.com、c.a.com 都能读到它；同时 HttpOnly 的 Cookie 对 JS 完全不可见，只会在 HTTP 请求中自动携带。

放宽：CORS

实际开发中跨源读取是常见需求，标准做法是 CORS（Cross-Origin Resource Sharing，跨源资源共享）。服务器通过一组 Access-Control-* 响应头声明允许哪些源访问。

CORS 把跨源请求分成两类：

类型 判定条件 浏览器行为
简单请求 方法为 GET / HEAD / POST，且只带少数安全头，Content-Type 仅限 application/x-www-form-urlencoded、multipart/form-data、text/plain 直接发出，服务器返回后由浏览器检查 Access-Control-Allow-Origin 是否匹配，不匹配则不把响应交给脚本
非简单请求 使用 PUT / DELETE 等方法、Content-Type: application/json、携带自定义请求头 先发一次 OPTIONS 预检（preflight），服务器返回允许的方法、头和源后才发出真实请求；预检不通过则真实请求根本不会发出

常用响应头：

响应头 作用
Access-Control-Allow-Origin 允许的源，可为具体源或 *
Access-Control-Allow-Methods 预检时声明允许的方法
Access-Control-Allow-Headers 预检时声明允许的自定义请求头
Access-Control-Allow-Credentials 是否允许携带 Cookie 等凭证。设为 true 时，Allow-Origin 不能是 *，必须写明具体源
Access-Control-Max-Age 预检结果可缓存多久，避免每次请求都预检

CORS 的放行是服务器授权的行为，能放开的是“读取响应”这一层。它不会改变浏览器自动携带 Cookie 的事实，因此不能当作访问控制手段。

其他放宽与绕过方式

  • document.domain：把页面的域名降级为更短的公共后缀（如 b.a.com 设为 a.com），使同一主域下的兄弟域被视为同源。该特性正被废弃
  • postMessage：跨窗口、跨 iframe、跨标签页通信的标准方式，接收方必须校验 event.origin，否则等于自己拆掉同源防线
  • JSONP：利用 <script> 不受同源限制的特性，通过回调函数接收数据，只支持 GET，且存在注入风险，已被 CORS 取代
  • 反向代理：把跨源请求变成同源请求，即由自己的服务器转发到目标服务器，在前后端分离的开发环境中常用

认证与授权

RBAC 模型

RBAC（Role-Based Access Control，基于角色的访问控制）的核心是“用户—角色—权限”三层关联：权限先授予角色，角色再授予用户。因此一个用户可以拥有多个角色，一个角色也可以被授予多个用户；一个角色可以拥有多个权限，同一个权限也可以被多个角色拥有。新增用户时只需分配角色，无需逐个配置权限。

graph LR
    user[用户] -->|拥有，多对多| role[角色]
    role -->|拥有，多对多| auth[权限]

SSO

SSO（Single Sign-On，单点登录）指用户在一处认证后，即可访问所有建立了信任关系的子系统，无需重复登录；登出时也可同步注销各子系统（Single Logout）。

常见实现是设立一个统一的认证中心（如 CAS、OAuth 2.0 / OIDC 授权服务器）：未登录的请求被重定向到认证中心，认证通过后由认证中心签发凭证（如票据或 Token），各子系统校验该凭证后放行。

Cookie

这是最经典的 Session 机制，基本流程如下

  1. 用户向服务器发送用户名、密码、验证码等信息登录系统
  2. 服务器验证通过后，为该用户创建一个 Session 对象并存储，同时分配一个唯一的 SessionID
  3. 服务器通过响应头 Set-Cookie 把 SessionID 发送给浏览器
  4. 浏览器将其保存为 Cookie。之后每次向该服务器发请求，浏览器都会自动带上这个 Cookie
  5. 服务器从 Cookie 中取出 SessionID，找到对应的 Session，从而识别用户

对于简单的业务，Session 数据可以存在服务器内存中；业务规模较大时，一般存放在分布式缓存（如 Redis）中；数据库也能存，但不太建议。

为保证 SessionID 的安全，应给 Cookie 设置 HttpOnly 标志，防止客户端脚本窃取；同时设置 Secure 标志，使其只在 HTTPS 连接下传输。

当服务扩展成多节点后，某个节点上的 Session 在其他节点上并不存在。常见解决方案有

  1. 粘性会话（session sticky）：用特定的哈希策略把同一用户的请求固定分配到同一台服务器。但该服务器宕机后，其上保存的 Session 会全部丢失。
  2. Session 复制：每台服务器都保存全量 Session。成本高，且复制有延迟。
  3. 集中存储：统一放到 Redis 等缓存中，并做好高可用、避免单点。
  4. Spring Session：用于在多个服务器之间管理会话的项目，可与 Redis、MongoDB 等多种后端存储集成，实现分布式会话管理。

CSRF 攻击

说明

CSRF（Cross-Site Request Forgery，跨站请求伪造，又称 XSRF）是指攻击者诱导受害者访问恶意页面，由该页面向受害者已登录的站点发起请求。浏览器会自动为请求带上该站点的 Cookie，服务器看到的是合法的登录凭证，于是误以为请求出自用户本人，从而以受害者身份执行了操作。

一次攻击通常包含以下步骤

  • 受害者登录 bank.com，并保留了登录凭证（Cookie）
  • 攻击者引诱受害者访问了 evil.com
  • evil.com 中有一段自动向 bank.com 发请求的代码。浏览器发送这个请求时会自动携带 bank.com 的 Cookie
  • bank.com 收到请求后校验凭证，确认有效，但无法判断该请求是否出于用户本意
  • bank.com 以受害者的名义执行了该请求

CSRF 能够成立的关键在于两点：浏览器会自动携带 Cookie，而请求的发送本身不受同源策略限制（同源策略只限制读取响应，不阻止请求被发送）。CSRF 通常是跨域的，因为外域更容易被攻击者掌控。但同站（同一主域下的不同子域）之间同样可能存在 CSRF，因此不能只按跨域来防范。

防护

CSRF Token

服务器在返回给用户的表单中嵌入一个随机、不可预测的字符串，即 CSRF Token，并同时把它记在服务端的 Session 里。用户提交表单时，前端必须一并提交该 Token（通常放在隐藏字段 _csrf 中），服务端比对两者是否一致。

由于同源策略禁止跨域读取页面内容，恶意站点既拿不到这个 Token，也无法猜测，因此伪造的请求会因缺少或错误的 Token 而失败。

SameSite Cookie

在设置 Cookie 时指定 SameSite 属性，控制跨站请求是否携带该 Cookie

  • SameSite=Strict：最严格，任何跨站请求都不发送。代价是从别的站点链接跳转过来时也处于未登录状态
  • SameSite=Lax：默认模式（现代浏览器在未指定时的默认值），仅顶层 GET 导航等安全的跨站请求携带，跨站 POST 与内嵌资源请求不携带
  • SameSite=None：关闭该限制，但必须同时设置 Secure（只通过 HTTPS 发送）

同源检测

既然 CSRF 多来自第三方站点，可以在服务端校验请求来源，拒绝不受信任的域。HTTP 中有两个可用于标记来源的请求头：

  • Origin：只包含协议 + 主机 + 端口，部分请求（如部分 GET 导航）不会携带
  • Referer：包含完整来源 URL，但可能因 Referrer-Policy 被截断或完全去掉，用户隐私设置也可能将其清除

这两个头由浏览器设置，前端脚本无法自定义（属于 forbidden header names）。因此不能只依赖其中一个，通常作为辅助校验，并与 Token 方案配合使用。

双重提交 Cookie

这是一种适用于无状态 API（如 JWT）的简化方案。用户登录后，服务器下发一个随机值，同时写入 Cookie 和响应体（或由前端读取该 Cookie）。前端在发起任何非幂等请求时，从 Cookie 中读出该值，放进自定义请求头或请求体一并发送；服务端比对请求头/体中的值与 Cookie 中的值是否一致。

恶意站点无法读取目标站点的 Cookie，因此无法在伪造请求中填上正确的值。

注意：该 Cookie 必须允许 JS 读取（不能设 HttpOnly），且若同一主域下存在可被攻克的子域，攻击者可以通过 Cookie 注入（cookie tossing）覆盖该值，因此实际使用较少。

JWT

JWT (JSON Web Token) 是目前最流行的跨域认证解决方案，是一种基于 Token 的认证授权机制。

JWT 由三部分组成

  • Header 头部，描述 JWT 的元数据，包含签名算法和 Token 类型

    通常由两部分构成

    • typ 令牌类型，也就是 JWT
    • alg 签名算法

  • Payload 载荷，存放实际需要传递的数据

    通常包含以下标准字段

    • iss JWT 签发方
    • iat JWT 签发时间
    • sub JWT 主题
    • aud JWT 接收方
    • exp JWT 过期时间
    • nbf JWT 生效时间，早于该定义时间的 JWT 不能被处理
    • jti JWT 唯一标识

    该部分默认不加密，因此不要把隐私信息放在里面

  • Signature 签名，用于确保 JWT 的完整性和真实性，由 header 和 payload 按指定算法计算得到

    其中的密钥存放在服务端中

这三部分通过 . 切分。

建议将 JWT 放在 LocalStorage 中，放在 Cookie 中会有 CSRF 风险。

该方案无状态，方便管理，能避免 CSRF 攻击，适合移动端应用，并且能实现 SSO（单点登录）功能——只要用户持有有效的 JWT，就能很方便地完成认证。

然而，JWT 在处理 退出登录/修改密码/修改权限/账户封禁/被迫下线/强制注销/主动注销 的场景比较麻烦。对此可以将 JWT 存入 redis（但违反了 JWT 的无状态原则），或者在 redis 中放一个黑名单，或者修改用户另外的专属密钥，或者经常轮换，等等。

若 JWT 需要续签，则可以采取客户端检测（不推荐）、每次请求都返回新 JWT（不推荐）、增加有效期或者设置到半夜（废话），或者返回两个 JWT —— accessJWT 和 refreshJWT。前者过期时间短，用于认证；后者过期时间长，用于刷新前者过期时间。

XSS 攻击

XSS（Cross-Site Scripting，跨站脚本攻击，缩写不写成 CSS 是为了避免与层叠样式表重名）指攻击者把恶意脚本注入网页，使其在受害者的浏览器中以目标站点的源为环境执行，从而窃取数据、冒充用户操作。

按恶意数据的来源可分为三类：反射型，数据来自 URL 参数或表单值，被服务端原样回显到响应中，需要诱导受害者点击特制链接；存储型，恶意内容被写入数据库（评论、昵称等），每次访问都会触发，危害最大；DOM 型，数据来自 URL 片段、document.referrer 等，由前端脚本直接写入页面，不经过服务端。

该攻击的本质在于把不可信的数据当成了代码执行，因此重点不在于拒绝用户输入，而在于按数据最终出现的上下文做输出处理：HTML 正文与属性做实体编码，URL 参数用 encodeURIComponent，写入 <script> 前先 JSON.stringify。不要用黑名单过滤，<script>、onerror、javascript: 的变形方式太多，必然漏。此外还可配合 CSP 禁止内联脚本、给 Cookie 设 HttpOnly、避免把不可信数据交给 innerHTML 等 API。
